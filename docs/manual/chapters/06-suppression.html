The audit and the hooks have separate exemptions, and neither honors the other's. The audit (chapter 02) skips whole files listed in a central allowlist or carrying a per-file marker. The PreToolUse hook (chapter 04) skips paths listed in otlcGuardian.ignorePaths. The web content hook and the runtime guard have no exemption at all. This chapter covers each mechanism from the code: loadAllowlist(), exemptionMechanism() and runAudit() in security/03-audit.js, and loadSettings(), isIgnoredPath() and settingsWeakening() in .claude/hooks/injection-guard-hook.mjs.

The central allowlist

loadAllowlist(rootDir) reads <projectRoot>/security/.audit-allowlist. If the file is missing or unreadable it returns an empty list without a warning. Each line is trimmed. Blank lines and lines that start with # are skipped. Every other line is split at its first #:

bin/guardian.js                    # reason: CLI tool, console.* output is its purpose
  • No # at all: .audit-allowlist:N missing reason, line ignored.
  • Text after the # does not start with reason: (case-insensitive): reason must start with "reason:", line ignored.
  • # reason: with nothing after it is accepted. The code checks for the prefix, not for any text after it.
  • A path that itself contains # cannot be listed, because the split happens at the first #.

Both warnings go to stderr through console.warn. The path is stored with backslashes turned into forward slashes. Nothing else is normalized.

exemptionMechanism() takes each scanned file's path relative to the project root, with forward slashes, and looks it up in the map. The match is exact:

  • no globs and no directory entries: tests/ exempts nothing;
  • no ./ prefix: ./bin/guardian.js never matches;
  • case-sensitive on every platform, Windows included, because it is a Map lookup.

The project root comes from findProjectRoot(). It walks up from the scan target, at most 8 levels, and stops at the first directory that holds any of .git, security/.audit-allowlist, package.json, requirements.txt, pyproject.toml or Pipfile. Since 1.3.1 a subdirectory scan therefore still reads the root allowlist (BUG-018). It also means a scan of a subpackage with its own package.json stops there and does not read an allowlist further up.

The audit-exempt marker

AUDIT_EXEMPT_MARKER is otlc-guardian:audit-exempt. exemptionMechanism() checks content.slice(0, 4096).includes(...): the first 4096 characters, which the docs call "4 KB". Any occurrence counts, in any comment style, a string literal, or prose. A file that only mentions the marker name near its top is exempt.

// otlc-guardian:audit-exempt  legacy route, tracked in BUGS.md

Two files in this repo show this. bin/guardian.js (line 9) and security/03-audit.js (line 22) both name the marker in their header comments, so both would be exempt by marker even without their allowlist lines.

The allowlist is checked first. A file that qualifies both ways is reported as [allowlist], the mechanism with a written reason. Neither mechanism is per rule: an exempt file is skipped by every pattern rule (scanFile() checks exemptPaths) and every analyzer rule (the fileCheckFn loop does the same, verified by the test "audit-exempt marker suppresses analyzer rules too" in tests/audit.test.js).

Where audit exemptions are reported

runAudit() works out every exemption before any rule runs and prints the result in the header of every run, whether or not anything was found:

    Files   : 12 scanned
    Exempt  : 3 (0 marker, 3 allowlist)
    [allowlist] security/02-code-security.js, security/03-audit.js, security/04-sql-guard.js

That is the output of a fresh guardian init project on 2026-11-10. The listed paths are relative to the scan target. In human mode these lines go to stdout. With --json they go to stderr, and the JSON on stdout carries exempt: { total, marker: [...], allowlist: [...] }.

The copied CI workflow (.github/workflows/security-audit.yml, step "Audit exemption visibility") runs the audit with --json and writes Files exempted from scanning: N to the GitHub step summary. It reports the count and does not fail the build when the count grows. The allowlist header says the same since the 1.5.0 fix; it used to claim CI failed.

What an audit exemption does not cover

The three project checks (DEP-001, DEP-002, WEB-002) are checkFn rules. runAudit() passes them the full file list, or the project root's files on a partial scan (BUG-041), without filtering out exemptPaths. An exempt file still counts as evidence for them: a health route in an exempt file still satisfies DEP-001, and a CSP header in an exempt file still clears WEB-002. No exemption removes a project check's finding.

Text that silences a rule (a defect)

WEB-002 fires when the project ships an nginx server block and nothing sets a Content-Security-Policy. nginxWithoutCsp() decides "something sets one" with CSP_ANYWHERE, a regex that matches the text content-security-policy (or helmet(, Talisman(, django-csp and others) anywhere in any scanned file or nginx config. A comment that only names the header, a TODO or a doc string, clears the finding. This is not a designed suppression and it shows up nowhere. It is logged as part of BUG-038 (OPEN).

SECURITY.md says: "If you find a way to add an exemption that does not show up in the summary or the allowlist, that is a Guardian security issue." By that standard this defect counts as one.

No other rule has an inline suppression comment. The comment on INJ-005b says "the global doc-exempt marker otlc-guardian:doc plus the per-file otlc-guardian:audit-exempt marker both already short-circuit it at the scanner layer". The audit has no code for otlc-guardian:doc; that comment is stale. Only audit-exempt works in the audit.

guardian update leaves a project's allowlist alone (PROJECT_OWNED_SECURITY_FILES). It copies the file only when it is missing, so a project's edits survive and Guardian's later changes to its own list do not arrive.

Hook exemption: otlcGuardian.ignorePaths

Since 1.5.0 this is the only exemption the PreToolUse hook honors. It is set in the project's .claude/settings.json:

{ "otlcGuardian": { "ignorePaths": [".planning/specs/injection-defense.md"] } }

How it matches

isIgnoredPath() canonicalizes the target with canonicalPath(): forward slashes, . and .. collapsed, any NTFS stream suffix removed. It then checks whether the result contains each entry, with backslashes in the entry turned into slashes. It is a substring match, so docs exempts every path with docs anywhere in it, and spec.md also exempts old-spec.md. The match ignores case on Windows and macOS only (CASE_INSENSITIVE_FS), so an entry never covers a different file on a case-sensitive file system. Since 1.5.0, empty strings and non-strings are skipped; an empty entry used to match every path and switch the hook off.

Where it is read

loadSettings() reads only <projectRoot>/.claude/settings.json. The root is CLAUDE_PROJECT_DIR, then the payload's cwd, then process.cwd(). An otlcGuardian block in settings.local.json has no effect. If settings.json does not parse, the hook warns on stderr and uses no exemptions and the default watch list, so a broken file never widens what is skipped.

What it covers

The hook applies it in one place, isWatched = t && !isIgnoredPath(t, settings) && isWatchedPath(t, settings). An ignored path drops out of the content verdicts for that path: the deny for a CRITICAL pattern a file write adds, the deny for content a shell command copies in, the ask for a Bash command, and the advisories. It does not cover the two self-protection checks, which run earlier and never consult it. A change that weakens .claude/settings*.json, and any change to the hook scripts or security/01-injection-guard.js, still asks even when an ignorePaths entry names that file.

Who may add an entry

A person. settingsWeakening() compares the settings before and after a Write, Edit or MultiEdit, and lists otlcGuardian.ignorePaths gains N entries as a weakening whenever an entry appears that was not there before; swapping one entry for another counts. The decision is ask, or deny when the session runs in bypassPermissions mode. A Bash or PowerShell command that writes, moves or removes a settings file, or a folder that holds one, is asked about every time, because the hook cannot see the result. Removing an entry is not a weakening, so the settings check does not flag it.

Settings that narrow the hook

These are not exemptions, but they shrink what the hook watches, and the same check guards them:

  • extendDefaults: false replaces the default watch list with watchPaths alone. Turning it off asks: "default watch list dropped".
  • Removing an entry from watchPaths asks: "watchPaths loses N entries".
  • disableAllHooks: true in either settings file, removing a Guardian hook, changing its matcher or command, or lowering its timeout asks. The hook reads settings.json and settings.local.json together for these, as Claude Code merges them.

guardian list-watched prints the effective list: defaults on or off, custom watch paths, ignored paths. It ends with the line "Exemptions: only otlcGuardian.ignorePaths in .claude/settings.json. The hook asks before an agent adds one."

History of the otlc-guardian:doc marker

VersionBehavior
1.1.0Added as a "doc-exempt marker" for security spec files that discuss injection patterns. A write whose content carried otlc-guardian:doc skipped the hook's scan.
to 1.4.1Unchanged. Any payload could exempt itself by including the marker, and the hook's warning text told the model the marker existed. Logged as BUG-021.
first 1.5.0 buildThe marker in the content was ignored, but a marker already on disk was honored. Review finding 3 showed the two-step bypass: write a marker-only file, then the payload.
1.5.0 (HEAD)The hook does not read the marker at all, in the content or on disk. ignorePaths is the only exemption. BUG-021 is SMOKE-TESTING.

Three tests in tests/hook.test.js hold this in place: a marker inside the content is denied; the two-step bypass is denied (in bypass mode); and "a marker on disk exempts nothing, even when a person put it there". The audit never had code for this marker (see above). README.md's fork advice still tells forks to keep both marker names "intact", though otlc-guardian:doc no longer does anything.

Where no exemption is needed, or none exists

  • Existing quotes in a file. The hook judges a write by what it adds compared with the file on disk (scanChange()). Editing a spec that already quotes attack phrases, or Guardian's own section in a CLAUDE.md, is not blocked. Adding a new copy of a pattern is. SETUP.md "Hook exemptions" says most documentation needs no exemption for this reason.
  • The web content hook (web-content-guard.mjs) reads no settings and has no exemption; its header says its tool list is "intentionally NOT configurable via .claude/settings.json yet". It is advisory only and never blocks. SETUP.md "Customizing the watch list" says "Both hooks honor an otlcGuardian config block"; the code shows only the PreToolUse hook does.
  • The runtime guard (security/01-injection-guard.js, injection_guard.py) has no exemption parameter or marker.

When to use one

Use an exemption only when the finding is wrong, and only in a way a reviewer can see. That is Step 3 of the OTLC-Guardian skill: "Never suppress a finding because the fix is inconvenient." For the audit that means an allowlist line with a real reason; it is preferred over the marker because it is one reviewable line in one file, takes precedence, and carries a written justification. Anyone with write access can add either, an agent included, because the hook does not watch security/.audit-allowlist or source files. The safeguards are the reason field, the exempt summary on every run, and CODEOWNERS review where it is set up. For the hook, the person approving the prompt decides.

Known-bug tests are not suppression. When a rule gets a case wrong, the case is logged in BUGS.md and kept as a knownBug() test in tests/audit.test.js, which fails the suite once the bug stops reproducing. The rule is never loosened to make the case pass.
