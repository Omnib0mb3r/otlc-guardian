The CLI is one file, bin/guardian.js, with no dependencies. It installs Guardian into a project by copying and merging files from its own source directory, and it never deletes anything. This chapter covers each command, what init writes where, how update differs from it, and how a project is taken back out. Everything here comes from bin/guardian.js at git HEAD 0fa32ce (1.5.0, unreleased).

The package and the source directory

package.json declares two executables: guardian (bin/guardian.js) and guardian-audit (security/03-audit.js run directly). It requires Node 22 or later (engines.node is >=22.0.0), has empty dependencies and devDependencies, and exports four modules: . (the injection guard), ./security, ./audit and ./sql. The files list ships bin/, security/, guides/, skill/, .claude/, .github/, the behavior and doc files, .env.example and .gitleaks.toml. tests/ is not in it.

The documented install is a clone plus npm install -g . (SETUP.md steps 1 and 2). Inside the CLI, ROOT is the directory one level above bin/, and every file init copies is read from there. runInit() prints it as Guardian source: at the top of every run, so the output always says which copy of Guardian a project received. Whatever that directory holds at the time is what gets copied, uncommitted edits included.

What init writes

runInit() works on process.cwd(); there is no target argument. It runs eight steps in a fixed order, and each step picks one of four ways to write.

security/package.json pins the scanner to ES modules (BUG-063)

The scanner and the other security/*.js files are ES modules with a .js extension, so Node takes their module type from the nearest package.json. In a project whose own package.json says "type": "commonjs" (npm 11's npm init -y default) the hook could not import the scanner, failed open, and scanned nothing. Since 2026-11-10 security/package.json ("type": "module") ships with the rest of security/: init copies it, update restores it like any Guardian-owned file, check lists it as required, and init warns (warnIfScannerNotEsm()) when a project already has one that does not say "module". The hook does not yet protect this file, so an agent can still rewrite it; that is a hook edit still to do (BUG-063).

Three things a project receives that are easy to miss:

  • Guardian's own allowlist. security/.audit-allowlist arrives with the seven entries the Guardian repo uses for itself. Three of them name files init just copied (security/02-code-security.js, 03-audit.js, 04-sql-guard.js), so those are exempt from the project's audit; a fresh install audits with Exempt : 3 (0 marker, 3 allowlist). The other four name bin/guardian.js and three files under tests/, and they exempt whatever the project keeps at those paths. See chapter 06.
  • Guardian's CODEOWNERS. .github/CODEOWNERS is the Guardian repo's file and names @Omnib0mb3r as owner of everything. In a project with no CODEOWNERS file of its own, that becomes the project's review rule.
  • Guardian's issue and PR templates, which describe Guardian, not the project.

The marker block in the behavior files

mergeMd() handles all four Markdown files. Guardian's section always sits between <!-- OTLC-GUARDIAN-START --> and <!-- OTLC-GUARDIAN-END -->, followed by a --- rule and three comment lines saying not to edit inside the markers. The content is the matching file from ROOT, trimmed.

  1. File missing. A new file is written with the marker block at the top and nothing above it. Since 1.1.1 a new file is sealed with markers too, so a second init is a no-op rather than a second append.
  2. File present, no start marker. Your content is kept with trailing whitespace trimmed, then one blank line, then the block.
  3. Start marker present. init prints Guardian section already present, skipping and leaves the file alone.

The test is existing.includes(marker): a file that contains the start marker anywhere, for example in a quoted example, counts as already merged.

.gitignore and .env.example use the shell-comment pair # OTLC-GUARDIAN-START / # OTLC-GUARDIAN-END. mergeGitignore() compares path tokens after removing an inline # comment (gitignorePathToken()), so your .env # local secrets line covers Guardian's .env. mergeEnvExample() compares keys (the text before =), so your value for a key is never joined by Guardian's. Comment lines from Guardian's templates are dropped. If nothing is missing, no block is written. A whole-file copy (the file was missing) has no markers.

The settings merge

mergeClaudeSettings() registers two hooks:

EventMatcherCommand
PreToolUseWrite|Edit|MultiEdit|NotebookEdit|Bash|PowerShellnode .claude/hooks/injection-guard-hook.mjs
PostToolUseWebFetch|WebSearch|mcp__firecrawl__crawl|mcp__exa__searchnode .claude/hooks/web-content-guard.mjs

For each one it:

  1. Migrates. It takes Guardian's command out of any block in the same event whose matcher differs from the current one. Your hooks in that block stay; the block is removed only if Guardian's entry was its last. This is the 1.5.0 migration that moves an old Write|Edit registration under the matcher that includes Bash and PowerShell.
  2. Finds or creates the block for the current matcher. Matchers are compared as sorted token sets (canonicalMatcher(), findMatcherBlock()), so Edit|Write and Write|Edit are one block, but a block with more or fewer tools is a different one.
  3. Adds Guardian's command to that block unless the exact same command string is already in it.

The file is written back only if a hook was added or moved, as 2-space JSON. If it does not parse, the function prints the parse error and the path of Guardian's reference copy, and throws. It never overwrites a file it cannot parse. It never adds the otlcGuardian block to an existing file; only a fresh copy carries one. Commands are compared as exact strings, which has consequences listed under open bugs (BUG-037).

What init never overwrites

init overwrites nothing. Every existing file is either merged or skipped. In detail:

  • Your text in the four behavior files, .gitignore and .env.example is never changed or removed. Only a block is appended, and only once.
  • Your hooks in .claude/settings.json are never removed or edited. The one exception is the migration step, which moves Guardian's own command entry out of a block with a different matcher; it can also drop a block that held only that entry.
  • Every existing file under security/, .claude/hooks/ and .github/ is skipped, including an old Guardian scanner or hook. Before 1.5.0 this was also true of update, which is BUG-025.
  • Files Guardian never creates (.cursorrules, .windsurfrules, .aider.conf.yml, copilot-instructions.md) are never written. The hook scans them; the CLI does not touch them.

How update decides

Up to 1.4.1, update was an alias for init (CHANGELOG 1.1.0: "alias for guardian init"). Because init never overwrites, a project that already had Guardian kept its first scanner and hooks forever, and no fix ever reached it. That is BUG-025, now SMOKE-TESTING. Since 1.5.0, update calls runInit({ refresh: true }), which changes three steps:

Targetinitupdate
Behavior files with a marker blockSkippedText from the start marker to the first end marker after it is replaced with current content. Everything before and after is written back byte for byte. No end marker: warning, file not touched. Identical result: not written.
security/*Existing files skippedrefreshOwnedDir(): missing files copied, a file whose bytes differ from ROOT's is replaced (UPDATED), identical files reported up to date
security/.audit-allowlistSkipped if presentSkipped if present (PROJECT_OWNED_SECURITY_FILES), copied if missing

.claude/settings.json, .gitignore, .env.example, .github/Identical in both. Settings get the merge and migration above; .github/ is never overwritten.

There are no backups. A local edit to a Guardian-owned file is overwritten without a prompt or a .bak copy; the help text says "git is the undo". Commit or stash before running it. refreshOwnedDir() compares raw bytes, so a file that differs only in line endings (for example after a git autocrlf checkout) is also replaced.

The first update after an init always reports each behavior file as refreshed, even with no change to Guardian's content. The comment header differs: init writes "To update, run: guardian init", the refresh writes "To update, run: guardian update". Later runs report up to date.

update prints the same "Guardian initialized successfully" banner as init. The per-file lines above it show what actually changed.

Update and the PreToolUse hook

The PreToolUse hook (chapter 04) protects the two hook scripts and security/01-injection-guard.js: any change by a file tool, or a Bash or PowerShell command whose write target is one of them or a folder holding one, asks for confirmation, and is denied in bypass mode. guardian update writes those files with copyFileSync() from its own Node process. The hook sees tool calls, not file system writes, so it never sees these writes. If an agent runs guardian update through Bash, the command text spells out no write target for the hook to read, so that is not caught either.

SETUP.md's advice follows from this: run update yourself. What it writes is limited to the content of ROOT, so the real question is who can change the Guardian source directory. That repo's own hook protects its own copies of the hook files and scanner.

Hook smoke test

When .claude/hooks/injection-guard-hook.mjs exists, smokeTestHook() runs it directly with spawnSync (10 second timeout) and pipes in a Write payload: a known CRITICAL phrase as content and .planning/__guardian_check_smoke.md as the path. It passes if the output contains PROMPT INJECTION BLOCKED or PROMPT INJECTION WARNING. The hook only returns a decision, so no file is written. A failure is a warning, not a required item, so check can exit 0 with a broken hook. The test runs the hook file, not the registered command, so it says nothing about the matcher or the command path.

Editor coverage

editorCoverage() prints one row per agent. Claude Code is FULL when CLAUDE.md, settings.json and both hooks exist, PARTIAL with only CLAUDE.md, and DISABLED otherwise. Codex CLI, Cursor, Aider, Continue and Windsurf are BEHAVIOR-ONLY when AGENTS.md exists. Gemini CLI is BEHAVIOR-ONLY only when both GEMINI.md and AGENTS.md exist, because GEMINI.md only points at AGENTS.md. This is all based on file existence.

Exit codes and failures

Most failures inside init and update are not caught. Any file system error (permissions, a locked file) and the invalid-settings throw end the process with a Node stack trace and exit code 1. The steps run in order, so a failure leaves a partial install. Run in a scratch directory with an unparsable .claude/settings.json, init had already written the four behavior files, .gitignore, .env.example and security/, had created an empty .claude/hooks/, and had copied no hook scripts and no .github/. Every step skips what is already in place, so fixing the JSON and running init again completes the install.

How agents are made to run Guardian

There are three layers, and only the last one does not depend on the agent following instructions.

  1. The global rule. C:\Users\michael\.claude\CLAUDE.md, section "Project Skills (Design and Guardian)", tells every session to invoke OTLC-Guardian for backend and full-stack code that touches auth, endpoints, user input, secrets, SQL or deployment, before committing or deploying, and to "run its audit rather than eyeballing the diff".
  2. The skill. C:\Users\michael\.claude\skills\OTLC-Guardian is a directory junction to C:\dev\Projects\otlc-guardian\skill\, so skill/SKILL.md is the live copy and edits in the repo take effect at once. Its description lists the trigger phrases (/guardian, "run guardian", "security review", "check for IDOR", commit, merge, deploy). Step 1 runs node C:\dev\Projects\otlc-guardian\security\03-audit.js <project-path> from the source repo, not the project's copy, so a skill-driven audit always uses the current rules even in a project whose security/ has not been updated. Step 3 covers suppression (chapter 06), Step 4 the self-audit checklist in CLAUDE.md.
  3. The project install. init merges Guardian's rules into the project's CLAUDE.md, AGENTS.md and GEMINI.md, which agents load at session start, and registers the hooks, which Claude Code runs on every matching tool call whatever the agent decides. The copied CI workflow runs node security/03-audit.js . --fail-on-error on GitHub, using the project's copy.

Uninstall

There is no guardian uninstall. A 1.2.0 branch had one (marker stripping, a surgical settings edit, byte-compare before delete); it was reverted in 1.2.1, and the reasons are recorded in the comment block after runInit(). Removal is manual, following SETUP.md § Uninstalling; README.md's "Uninstalling" section summarizes it and points there.

The old README instructions blanket-deleted the merged rule files, which destroyed any rules the user had written before init. That is BUG-013, RESOLVED. The current text says to delete only the marker block, never a merged file, and to delete Guardian's files one by one, never with rm -rf security/ or rm -rf .claude/hooks/.

In short: remove the marker blocks from the four Markdown files, .gitignore and .env.example; remove Guardian's two command entries from .claude/settings.json; delete Guardian's files by name; optionally remove the workflow and run npm uninstall -g otlc-guardian.

Where the current uninstall text and the code disagree

1. SETUP.md Step 1 says a file without markers was created whole by Guardian and can be deleted. That holds for .gitignore and .env.example, which init copies whole. It is wrong for the four Markdown files: mergeMd() seals a new file with markers too. A Markdown file Guardian created has the marker block at the very top with nothing above it. 2. SETUP.md Step 3 lists six files to delete and leaves out security/04-sql-guard.js (README.md's list includes it) and security/.audit-allowlist. 3. Step 4 covers only .github/workflows/security-audit.yml; init also copies CODEOWNERS, two issue templates, PULL_REQUEST_TEMPLATE.md and secret_scanning.yml. 4. Step 2 does not mention the otlcGuardian block that a fresh settings copy contains.

Do it by hand, and in this order. While the hook is registered, an agent that removes Guardian's settings entries or deletes the hook files or scanner gets a confirmation prompt, or a denial in bypass mode. Remove the registrations in settings.json first, then delete the files. If the files go first, Claude Code still runs the registered node .claude/hooks/... command on every matching tool call, and Node fails because the file is missing. Per the hook's failure design that is a non-blocking hook error, reported on every matched call until the entries are removed.

What the tests verify

tests/init.test.js (30 tests, all passing on 2026-11-10) imports the helpers exported from bin/guardian.js and runs each in its own mkdtemp directory. It covers: canonicalMatcher() and findMatcherBlock() set comparison; gitignorePathToken(); mergeMd() keeping your content and staying idempotent, and in refresh mode replacing only the block, keeping text above and below byte for byte, and staying idempotent; mergeClaudeSettings() refusing invalid JSON without writing, keeping your hooks, joining a reordered matcher block, staying idempotent, and migrating a pre-1.5.0 Write|Edit registration exactly once; refreshOwnedDir() replacing a stale file, copying a missing one and keeping .audit-allowlist; copyDirSafe() never overwriting; key-based dedupe in mergeEnvExample(); and copyIfNew(). tests/agents-md.test.js covers editorCoverage().

Not covered by any test: runInit() end to end, the partial install after an invalid-settings abort, runCheck() and its exit codes, the router, the custom-matcher and $CLAUDE_PROJECT_DIR cases of BUG-037, and the uninstall procedure.

Known open bugs

Open on 2026-11-10

BUG-060 (OPEN): init copies Guardian's whole .github/ folder, including a CODEOWNERS that names Guardian's maintainer, and Guardian's own allowlist entries. BUG-061 (OPEN): an invalid .claude/settings.json stops init and update with a stack trace after earlier steps are written. BUG-062 (OPEN): guardian check exits 0 and reports a correct install when the hook smoke test fails, and never reads the registration; CI uses it as a gate.

BUG-028 (OPEN): the registered hook command, node .claude/hooks/injection-guard-hook.mjs, is relative to the current directory. After a session changes directory, Node cannot find the file. The $CLAUDE_PROJECT_DIR form has not been tested on Windows, so init still writes the relative form. BUG-034 (OPEN): Bash is now in the PreToolUse matcher, so after a cd every Bash call hits BUG-028 and reports a hook error. BUG-035 (OPEN): an "ask" decision waits for a person, which stalls an unattended worker in default and acceptEdits modes; only bypass mode turns ask into deny. BUG-037 (OPEN): the update migration removes Guardian's command from any block whose matcher differs from the default, including a wider custom matcher a user chose, and re-registers it under the default. Commands are compared as exact strings, so a project that changed the command to the $CLAUDE_PROJECT_DIR form gets the relative form added as a second registration. BUG-045 (OPEN): the hook's settings protection treats the $CLAUDE_PROJECT_DIR command form as a weakening, so making that switch by hand also gets a prompt. BUG-027 (IN-PROGRESS): the hook files and scanner can be written by the agent they guard. The in-hook half landed in 1.5.0; update's own writes are outside it (see Update and the PreToolUse hook). BUG-025 (SMOKE-TESTING): update now overwrites Guardian-owned files; it has not yet been run on another real project. The CHANGELOG says 1.5.0 has not been rolled out to any other project.
