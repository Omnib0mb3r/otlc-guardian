Guardian is read from outside this repo in more places than it is installed. Most sessions on this PC never get a copy of Guardian: they load the skill, which runs the audit straight from C:\dev\Projects\otlc-guardian. So a change to the audit's command line, output or rule ids reaches every project at once, with no guardian update in between.

Planned: the hard-no hook planned

The content hook (chapter 04) judges a shell command by what it spells out. The routes it leaves out on purpose (variable, computed and glob targets, inline interpreter code, script files, encoded content, git operations that replace files without naming them, and writes from processes such as guardian update) are inputs for a hard-no hook in Lane 5 of the Self-Growing Gate spec (TODO.md). DevNeural already runs a cross-project write guard as a PreToolUse hook; the hard-no hook extends or sits on that guard and is hosted by DevNeural, with the boundary agreed with DevNeural's Lex first. Nothing is built: the spec is research and a plan for Michael's approval.

When Guardian changes

  • A change to the audit's command line, output, rule ids or rule count updates skill/SKILL.md in the same commit, and DevNeural's Lex is told, because DevNeural's chapter 12 describes it.
  • A change to the runtime guard's exports or violation shape is a breaking change for importing applications: note it in CHANGELOG.md under "Changed" and keep a compatibility field for one minor version, as legacyId does.
  • A change to the hooks or the scanner reaches installed projects only through guardian update, run in each project by a person. The hook denies an agent's change to those files in bypass mode (chapter 04).
  • When 1.5.0 is pushed, DevNeural's Lex is told again (BUG-041 is fixed in eebc4f9; chapter 12 needs the 1.5.0 changes).
