The runtime layer is four files in security/. 01-injection-guard.js is the scanner: it reads a string, normalizes it, runs 28 injection rules and 16 secret rules over every decoded view, and returns the findings. injection_guard.py is its Python port. 02-code-security.js holds Express helpers (headers, request ids, a logger, a rate limiter, error shapes, a health route). 04-sql-guard.js is a tagged-template SQL helper that turns every interpolation into a bound parameter. Nothing in the layer has a dependency outside the Node or Python standard library.

This chapter describes the code at git 0fa32ce plus the 1.5.0 working tree (unreleased). Where the README, SECURITY.md or SETUP.md say something different, the code wins and the gap is listed in Code versus docs.

How one scan runs

Every pattern is a single regex or a linear comment walker, and every normalizer pass is linear in its input, so the cap is a memory bound rather than a guard against slow regexes (comment above MAX_SCAN_LENGTH). Each rule reports at most once per call: scan() keeps the first match only.

Order of work: type check (a non-string throws GuardianError("guardInput requires a string.")), length cut, scan(input, "all"), reportViolations(), callbacks, secret block, critical block, sanitize(), then a second scan(sanitized, "injection"). HIGH and MEDIUM findings never block: they are reported and the sanitized string is returned.

Because hasCritical counts secret findings, a caller that sets blockOnSecrets: false but keeps blockOnCritical: true still gets a throw on a secret, with the message for a critical injection. The Python port does not do this (see The Python port).

guardOutput(output, options)

Options: blockOnSecrets (default true), onViolation, context (default "AI output"). It runs scan(output, "secrets") and then scan(output, "injection") as two separate calls, reports both sets, fires the callback for both, and throws only on secrets. The thrown error carries the secret violations only. Injection findings in output are informational: the function returns output unchanged, never sanitized.

sanitize(input)

Removes chat role tags (opening or closing system, assistant, human, user in angle brackets), [SYSTEM], [INST], the Llama SYS markers, a run of three hashes followed by System, Instruction or Prompt, three hyphens followed by SYSTEM, and every character in the strip set (see Normalizer). It does not type-check, so a non-string throws a TypeError from .replace.

The heading strip is wider than detection. Since 1.5.0, GUARD-INJ-019 only fires on the colon form, but sanitize() still removes the words, so "### System Overview" comes back from guardInput() as " Overview". Verified by running it.

reportViolations(violations, context)

Prints a PROMPT INJECTION DETECTED block on console.warn (severity, id, matched text per finding) and a SECRET LEAK DETECTED block on console.error (id and label, no secret text). An empty array prints nothing. This is plain console text, not the JSON logger from 02-code-security.js; a project that needs structured logs passes onViolation.

injectionMiddleware(options)

Express middleware. For each field in options.fields (default message, prompt, query, input, content) that is truthy on req.body, it replaces the value with guardInput(value, { ...options, context: "METHOD path" }). A GuardianError becomes a 400 with { success: false, error: { code: "ERR_INJECTION_DETECTED", message: "Input rejected by security guard." }, requestId }; requestId is req.requestId or a fresh UUID. Any other error goes to next(err). A truthy non-string field (a number, an object) fails the type check and gets the same 400. The body must already be parsed (express.json() before it).

GuardianError

name is "GuardianError", violations is the array that caused the block, timestamp is the ISO time of construction.

The comment walker (027, 028)

These two rules carry a match and a matchAll built by commentMatcher(open, close) instead of a regex. It finds each opener with indexOf, finds the next closer, tests the keyword regex on that one comment, and moves past the closer. When no closer follows an opener the search ends, because no later opener can close either. Cost is linear. The regex form it replaced was cubic on a flood of unterminated openers (44 KB took 16 s; BUG-023). pattern on these entries (/<!--/, /\/\*/) is only a descriptor for callers that print pattern.source.

Normalizer, decode views and caps

scanViews(text) returns eight strings in a fixed order. A view that does not apply is the empty string, so view N of one text lines up with view N of another (scanChange() depends on that). normalizeForScan() keeps view 1, adds every later view that is non-empty and not already present, and joins them with newlines. scanChange(): judging what a change adds

scanChange(before, after, mode) answers "does this edit add a finding", which a whole-file scan() cannot: a file that already quotes a pattern (a security document, Guardian's own CLAUDE.md section) would be flagged on every edit, and judging by rule id alone would let a second copy of an already-present rule through. The PreToolUse hook calls it for every Write, Edit and MultiEdit it judges (chapter 04).

Steps

  1. A non-string after returns an empty result. A non-string before is treated as "" (a new file, judged in full).
  2. changedWindows() trims the common prefix and common suffix (compared by UTF-16 code unit) but keeps up to 2048 characters of each on both sides. The result is an old window and a new window. A small edit to a large file costs a small scan, and a payload appended past the 1 MB mark of the whole file is still inside the new window.
  3. scan(newWindow, mode) lists the candidate findings.
  4. scanViews() runs on both windows (each capped at 1,000,000).
  5. Each candidate is kept or dropped:
    • GUARD-INJ-OVERSIZE is always kept: unscanned text is never "already accounted for".
    • GUARD-INJ-UNICODE is kept when the new window holds more detect-set characters than the old one.
    • Every other rule goes through firstAddedMatch(): for each view index, the rule's matched strings in the old view are counted into a multiset, then the new view's matches consume those counts. The first match with no count left is the added one. For an injection finding matched is replaced with that new string; a secret finding keeps its redaction.
  6. The return is { violations, hasSecrets, hasCritical } over the kept findings only.

What this gives (each case has a test in tests/injection-guard.test.js, group "scanChange()"): rewriting a file that already quotes a pattern is clean; adding a second copy is a finding; swapping the quoted example for a different payload is a finding; a payload completed across old and new text is a finding; an encoded copy of a quoted pattern is a finding (it is a new string in a decoded view); removing a pattern is never a finding.

Known limits

  • Moving is not adding (BUG-042). The judgement is a count. Cutting an already-quoted pattern out of a data context (an example block) and pasting it into a live instruction in the same window leaves every count unchanged, so nothing is reported.
  • The window can be crossed (BUG-046). The multi-word rules allow any run of whitespace between words. If the existing half of a phrase sits more than 2048 characters of whitespace away from the added half, the window cuts the old half off and neither window holds the whole match.
  • A new window over 1,000,000 characters always yields GUARD-INJ-OVERSIZE (MEDIUM), which the hook treats as advisory.

04-sql-guard.js: the parameterized SQL helper

A zero-dependency tagged template that makes the parameterized query the easy path. It is not a filter: it never inspects values and never rejects SQL text. The static audit (03-audit.js) is what flags string-built SQL; this helper is the safe replacement.

Exports

ExportUse
sqlTag bound to postgres: sql`SELECT * FROM users WHERE id = ${id}` gives { text: "... = $1", values: [id], driver: "postgres" }.
createSqlHelper({ driver })Returns a tag bound to "postgres", "mysql" or "sqlite".
sql.identifier(name, allowList)The one way to put a column or table name into the text. Also on every tag from createSqlHelper.

Drivers

DriverLibraryPlaceholderIdentifier quote
postgrespg$1, $2, ..."name"
mysqlmysql2?`name`

Behavior

  • Every interpolation becomes one placeholder and one entry in values, whatever it is: strings, numbers, 0, "", null, undefined, objects, buffers. An array is one value, not a list; an IN list needs the driver's own form (for example = ANY(${arr}) on postgres).
  • A nested sql`...` result is inlined; placeholders are renumbered and values concatenated in document order, in the outer tag's dialect.
  • The result carries toPostgres(), toMysql(), toSqlite(), which re-render the stored parts without mutating the original. The parts sit under a non-enumerable Symbol key, so spreading or JSON.stringify does not expose them, and a user object cannot pass itself off as a query.
  • Text between interpolations is kept byte for byte.

What it refuses (all throw Error)

  • createSqlHelper() with any driver outside the three.
  • sql.identifier() when the allow-list is not a non-empty array.
  • sql.identifier() when the name is not a string matching ^[A-Za-z_][A-Za-z0-9_]*(\.[A-Za-z_][A-Za-z0-9_]*)?$ (an optional single schema. prefix). This check runs before the allow-list check, so a bad name is rejected even if someone put it on the list.
  • sql.identifier() when the name is not on the allow-list. There is no fallback to a default.

A bare string in ORDER BY ${col} is a value, not an identifier, so it binds as a parameter (test: "raw string interpolation in ORDER BY is a parameter, NOT an identifier"). No Python equivalent exists; the README points Python users to SQLAlchemy or DB-API execute(sql, params).

What the tests verify

node tests/injection-guard.test.js passed 106 checks and node tests/sql-guard.test.js passed 40 on this tree (run while writing this chapter).

  • Injection: one or more cases per rule family, the GUARD-INJ-009 user exception, legitimate questions that must not fire, empty string.
  • Bypasses: fullwidth, zero-width, percent-encoding, word joiner, tag characters (payload found and GUARD-INJ-UNICODE raised), Cyrillic lookalikes, ordinary Cyrillic text not flagged, stray %, embedded base64, entities, markdown emphasis, emoji with a variation selector not flagged, oversize input, a payload at 150 KB.
  • Time: unterminated comment floods for 027 and 028 and a connection-string prefix flood for SEC-011 stay fast; 027 needs the keyword inside one comment.
  • Secrets: each provider format, including the 1.5.0 additions; the legacy OpenAI rule does not double-fire; public key headers and credential-less URLs do not fire.
  • Ids: every scanner id starts with GUARD-, none is an audit id, legacyId is present.
  • 019 and 020: ordinary headings and front matter do not fire, template delimiters do.
  • scanChange(): eleven tests, covering the cases listed in scanChange() plus the reported text being the new one, a large file staying cheap, an append past 1 MB, and new versus existing invisible characters.
  • Guards: clean pass-through, truncation, CRITICAL throw with a violations array, non-string throw, guardOutput secret detection and reflected injection, no throw with blockOnSecrets: false.
  • SQL: placeholders per dialect, text preserved, injection payloads bound as values, identifier allow-list and shape checks, nested composition, values passed through unfiltered (including 0, "", null), pure dialect conversion.

Not covered by any test: injectionMiddleware(), everything in 02-code-security.js, and the whole Python module.

Open bugs

Open on 2026-11-10

BUG-029 (OPEN). Scanner bypasses still open: the 64-candidate base64 cap can be spent by decoys, chained encodings (two decode steps) pass because each view is one step, and the confusables table has gaps.

BUG-042 (OPEN). scanChange() judges by counts, so moving an already-quoted pattern into a live directive is not a new finding.

BUG-046 (OPEN). Whitespace padding longer than the 2 KB CHANGE_CONTEXT window separates the old half of a phrase from the added half, and neither window sees the whole match.

BUG-043 (OPEN). False denies from the hook on scanner matches: ### System: Billing, ### Prompt:, a --- System --- line, prose that mentions wrapping text in a user role tag, and a CLAUDE.md line that quotes a pattern as data. Rules 015, 019 and 020 match these by design; the fix belongs to the rules or to the hook.

BUG-023, BUG-024, BUG-026 (SMOKE-TESTING). The cubic comment rules, the eight normalizer bypasses and the missed secret formats are fixed in the 1.5.0 tree and covered by tests; they stay open until verified in a real project.

BUG-049 (IN-PROGRESS). scan() with an unknown mode runs no rules and returns clean, so a typo turns the guard off; a non-string returns clean too. Fixed in the Python port (live: ValueError, TypeError); the Node fix is staged, not yet live (chapter 04, Staged fixes).

BUG-050 (OPEN). guardInput with blockOnSecrets: false still throws on a secret, because hasCritical counts secret findings, and the message calls it an injection. The fix is staged, not yet live (chapter 04, Staged fixes); the Python port already keeps the two apart, and a parity test now checks it.

BUG-027 (IN-PROGRESS). The hook now protects the scanner file and itself; the remaining half sits outside this chapter.

Detection is pattern-based. A reworded instruction that matches none of the 28 rules passes, and the substring rules (023, 024, 028 and others) fire on ordinary mentions. Neither has a bug entry. CHANGELOG.md lists the first under known limits; the second follows from the regexes having no word boundaries.
