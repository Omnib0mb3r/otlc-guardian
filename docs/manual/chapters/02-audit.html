What the audit is and is not

security/03-audit.js is a standalone Node script (ESM, no dependencies beyond fs and path). It walks a directory, reads source files as text and reports places where the code matches a known bad shape: a hardcoded key, a silent catch, SQL built by concatenation, a route handler that writes to the database without checking who is calling, and so on. It is a review and CI tool. It runs once, prints a report, and exits.

It is not part of a running application. Nothing in it is imported by the runtime guard (security/01-injection-guard.js), the hooks or the SQL helper, and it never executes the code it scans. Its only subprocess is git, for DEP-002. It does not parse JavaScript or Python into a syntax tree: pattern rules are regular expressions, and the analyzers find route handlers by matching signatures and then balancing braces (JavaScript) or reading indentation (Python). A clean result means none of the 42 shapes was found. It does not mean the code is secure, and the analyzers say so in their own comments (see Route-handler analyzers).

The file exports runAudit and AUDIT_RULES, and package.json exposes it as otlc-guardian/audit and as the guardian-audit bin. The CLI entry at the bottom of the file runs only when the file is the program Node was started with (isEntryPoint(), comparing real paths, so a start through npm's bin symlink counts); until 2026-11-10 it also ran on every import (BUG-053). Every test in tests/audit.test.js spawns it as a subprocess instead of importing it.

One run, start to finish

The order inside runAudit():

  1. scanRoot = path.resolve(target); projectRoot = findProjectRoot(scanRoot).
  2. Status header printed: target, project (only when it differs from the target) and the live rule count line.
  3. loadAllowlist(projectRoot).
  4. collectFiles(scanRoot, allExtensions), where allExtensions is the union of every rule's fileTypes.
  5. Each collected file is read once to decide exemption with exemptionMechanism(). File and exempt counts are printed, then every exempt path by mechanism, then each per-rule exemption as [allowlist rule] <path> [IDS].
  6. Pattern rules, in AUDIT_RULES order, over the files whose extension is in the rule's fileTypes.
  7. Analyzer rules, same file filter.
  8. Project rules.
  9. Report, then process.exit(1) if --fail-on-error was given and any finding is CRITICAL or HIGH. Otherwise runAudit() returns the findings array and the process ends with code 0.

Command line

node security/03-audit.js [target] [--json] [--fail-on-error]

Which files get scanned

collectFiles(rootDir, extensions) builds the list. It is called once from the scan root with the union of all rules' fileTypes, which today is .js .ts .jsx .tsx .mjs .cjs .mts .cts .py .env .json .yaml .yml .html .htm .vue .svelte, plus every file a rule with includePatterns names by path (includedByRule(); today AGT-002's instruction files, below).

  • Extension match. A file is kept when path.extname(name).toLowerCase() is in the list. A name with no extension, such as Dockerfile, is never collected. The one exception is a bare .env (DOTENV_FILE), kept by name for DEP-002 (BUG-039, fixed 2026-11-10). No pattern or analyzer rule reads it, because no fileTypes list contains the empty extension, so the secret rules still never read .env, .env.local or .env.production: a gitignored .env is where secrets belong. The .env entry in SECRET_FILE_EXTS only matches names like prod.env.
  • Path match (BUG-002). A rule with includePatterns reads only the files whose path inside the project, with a leading /, matches one; its fileTypes is unused (appliesTo()). collectFiles(rootDir, extensions, byPath) keeps such a file whatever its extension, so a .md file is collected only when it is an instruction file. A file collected this way is read by its rule alone: collectedByPath() keeps it out of every project check's evidence, because Guardian's own CLAUDE.md asks for a /health endpoint and DEP-001 would read that as the app having one.
  • Skipped directories. SKIP_DIRS is matched against the entry name at any depth: node_modules, bower_components, vendor, venv, .venv, site-packages, dist-packages, dist, build, .next, out, target, __pycache__, .pytest_cache, .mypy_cache, .ruff_cache, .turbo, .cache, coverage, .git. Dependency code is left to npm audit and pip-audit. env is deliberately not on the list because real projects use it for source. Other dot-directories (.github, .claude) are walked.
  • Symlinks. The walker uses readdirSync(..., { withFileTypes: true }) and only follows entries whose isDirectory() or isFile() is true. A symlink reports neither, so symlinked files and directories are skipped.
  • Unreadable directories are skipped silently (the readdirSync error is caught and the directory contributes nothing). Unreadable files are skipped by each pass the same way.
  • Single-file target. If the target is a file, collectFiles() returns [target] when its extension is wanted and [] otherwise. Before BUG-041 it called readdirSync on the file, failed, and scanned nothing. The source comment names the use case: a commit hook auditing changed files.
  • Missing target. statSync(..., { throwIfNoEntry: false }) returns nothing, the walk's readdirSync fails, and the list is empty. The run reports 0 files and no issues.

Scan root and project root

Two directories matter, and since 1.3.1 (BUG-018) they are kept apart:

  • scanRoot: the target the user named. The walker collects files only from here, and report paths are relative to it.
  • projectRoot: found by findProjectRoot(), which walks upward from the scan root (at most 8 levels) and stops at the first directory holding any of .git, security/.audit-allowlist, package.json, requirements.txt, pyproject.toml, Pipfile. With no marker anywhere it falls back to the scan root.

The project root is used for three things: the central allowlist (loadAllowlist(projectRoot), and allowlist entries are matched as paths relative to it), the manifests that DEP-001's looksLikeHttpServer() reads, and the evidence for project checks that prove an absence. That last point is BUG-041 (fixed 2026-11-10): a project check declares evidence: "project" when its finding means "nowhere in the project". On a partial scan (projectRoot !== scanRoot) such a check receives collectFiles(projectRoot, allExtensions), computed once and shared, and its finding names the project root. DEP-001 and WEB-002 carry the flag. DEP-002 is a presence check (a .env exists), so it keeps the scanned files: a hit there is true of the part the user asked about. Before the fix, auditing DevNeural's 07-daemon/src/capture/hooks reported DEP-001 although DevNeural serves GET /health elsewhere in the repo.

The scan does not widen to the project

Running the audit from a subdirectory scans that subdirectory only. Pattern and analyzer rules never look outside the scan root. Only the absence checks and the manifest lookup see the whole project.

Test-file detection

Rules aimed at production code carry excludePatterns: TEST_FILE_EXCLUDES. The list, defined at the top of the file so the rules can reference it:

RegexMatches
/\.test\./i*.test.* (Jest, Vitest)
/\.spec\./i*.spec.* (Mocha, Jasmine, Karma)
/[\/\\]__tests__[\/\\]/ia __tests__ directory
/[\/\\]tests?[\/\\]/ia test or tests directory
/[\/\\]spec[\/\\]/ia spec directory (RSpec)
/[\/\\]test[_-][^\/\\]+$/itest_*.py, test-*.js
/[_-]test\.[a-z]+$/i*_test.py, *-test.js

excludedByRule() tests the patterns against the path inside the project, with a leading / (/src/a.test.js), so a tests/ folder at the project root matches. The [\/\\] class makes the directory forms work with Windows backslashes. Rules that apply the exclusion: SEC-006, CFG-001, CFG-002, CFG-003, ERR-003, INJ-002, AUTHZ-001 to AUTHZ-005, AUTHZ-011, AUTHZ-013, VAL-001, VAL-002, WEB-001, TS-001. Every other rule, including all hardcoded-key rules, fires in tests too. Folders above the project root do not count: before the fix the absolute path was tested, so a project under a folder called test, tests or spec lost these rules on every file (BUG-052, fixed 2026-11-10).

Every entry in AUDIT_RULES has id, category, severity, description and fileTypes. Which of three further fields it sets decides its kind, and runAudit() runs the kinds as three separate loops. The status line counts them the same way: filter((r) => r.pattern), r.fileCheckFn, r.checkFn.

The analyzer kind exists because missing authentication and IDOR are absences inside a block ("nowhere in this handler is there an auth check"), and a regular expression cannot express that across arbitrarily nested braces. The source comment above findRouteHandlers() records the reasoning: a regex approximation would fire on unrelated files, and a security tool that cries wolf gets switched off.

Exemptions and project checks (BUG-059): an absence check (evidence: "project", DEP-001 and WEB-002) reads exempt files too, so an exempt file can still provide the "health" evidence for DEP-001 or a CSP for WEB-002; a presence check (DEP-002) leaves exempt files out. Neither reads a file collected by path (an instruction file).

Route-handler analyzers

JavaScript and TypeScript (AUTHZ-001, AUTHZ-003, VAL-001)

findRouteHandlers(content) finds handlers by four signatures in HANDLER_SIGNATURES:

  • app|router|server|api .get|post|put|patch|delete|all( (Express, Fastify, Hono style). lastInlineHandler() takes the inline function (=> { or function (...) {) whose block is the call's last argument, within 40,000 characters; everything before it in the call is the handler's head (path and route-level middleware). A handler passed by name has no block there and is skipped. Before BUG-070 (fixed 2026-11-10) the body was the first { after the signature, so an options object in middleware (passport.authenticate("jwt", { session: false })) was read as the handler.
  • export [async] function GET|POST|PUT|PATCH|DELETE( (Next.js App Router).
  • export const GET|POST|... = [async] ( (App Router, arrow form).
  • export default [async] function name( (Pages Router, Vercel).

For the last three (skipParams: true) the parameter list is skipped with skipParenGroup() first, so a destructured parameter such as { params } is not taken as the body. extractBlock() then balances braces from the opening {, skipping // and /* */ comments and single, double and backtick strings (template ${} contents are treated as string text). Handlers fully inside an earlier handler are dropped as inner callbacks. Each check then works on the handler body text with lists of regexes:

RuleFires when
AUTHZ-001The body matches a SIDE_EFFECT_PATTERNS entry (ORM .create/.update/.delete/.save/...(, email senders, stripe.*.create, fetch(, axios.post/put/patch/delete(, execute(, query(, writeFile() and no AUTH_PATTERNS entry (requireAuth, getSession(, getServerSession(, jwt.verify(, req.user, passport., auth(), an authorization header read, api_key, and others) in the body, in the route-level middleware (router.delete(path, requireAuth, handler), an array, or an inline middleware), or in an auth mount on the same object registered earlier (router.use(requireAuth), app.use("/api", verifyToken); jsAuthMounts(), handlerIsAuthenticated()). AUTHZ-003The body authenticates, reads a caller-supplied id (params.id, req.params.*Id, req.query.*Id, body.*Id, searchParams.get("...Id")), has a side effect, and hasJsOwnership() finds no ownership evidence. That evidence must tie the object to the verified caller (JS_PRINCIPAL: req.user, req.session, ctx.state.user, session.user, currentUser, user, me, auth(), token.sub and similar): an owner, user, author, tenant, team, account, customer, org or workspace column compared with or bound to the caller (userId: req.user.id, doc.ownerId !== req.user.id, .eq("user_id", req.user.id)), the caller on the left, or a name bound from the caller earlier in the body (const userId = req.user.id then where: { id, userId }; principalBoundNames()). VAL-001The body reads the request body (req.body, request.body, await req.json(), ctx.request.body, c.req.json()), reaches a side effect, and calls no schema parser (.parse(, .safeParse(, async forms, *Schema.*parse, validateRequest, zodResolver, ajv, yup, joi., valibot, model_validate).

The lists err toward silence on purpose: a broad "auth is present" reading suppresses a finding, which the source calls the safe direction for a noisy rule. A word anywhere in the body counts, so a comment such as // TODO role check inside a JS handler clears AUTHZ-003 (comments are skipped only by the brace matcher, not by the content checks).

Python (AUTHZ-011, AUTHZ-013), new in 1.5.0

findPythonHandlers(content) treats a function under a route decorator (@x.get|post|put|patch|delete|route|api_route() as a handler. It walks down at most 40 lines to the def at the same indent, balances brackets to find the end of a multi-line signature, takes every following line indented deeper as the body, and adds any decorators stacked above. # comments are stripped (stripPyComments()) so a "# TODO: add auth" note does not count. Auth and ownership are searched across decorators, signature and body (FastAPI auth usually lives in Depends(...)); side effects only in the body.

  • AUTHZ-011 (checkPyMissingAuth()): a body side effect (pyHasSideEffect(): db.add/commit/delete..., a database execute unless the body builds a select and no write (PY_SQL_READ, PY_SQL_WRITE; an execute of a statement built elsewhere still counts, BUG-032), Django .objects.create/update/delete, .save(, Mongo writes, send_mail, requests|httpx.post/put/patch/delete, file writes, shutil, os.remove, subprocess.) with no PY_AUTH_PATTERNS match. An API key counts when it is read from the request or verified (x-api-key, APIKeyHeader, Depends(get_api_key), verify_api_key), not on a bare api_key mention. isPublicPyRoute() skips a route as public when one path segment is login, logout, signin, signup, register, health, healthz, healthcheck, ping, metrics, token, magic, otp, verify, reset, callback or webhook(s), alone or joined by - or _ (/auth/login, /users/verify-email); /api/tokens/{token_id} is not public. pyAuthedRouters() honors router-level auth only for a router built in the same file (name = APIRouter(...) or FastAPI(...)) whose dependencies=[...] list is itself auth, and only for handlers decorated with that name. Before BUG-031 (fixed 2026-11-10) the public list matched substrings, any api_key mention was auth, and any dependencies=[Depends( in the file, Depends(get_db) included, silenced every handler.
  • AUTHZ-013 (checkPyMissingObjectAuthz()): authenticated (or on a router whose own dependencies are auth), an id from the caller ({doc_id}, <int:doc_id>, a *_id parameter, request.args/json/... ["...id"]), a side effect or any database execute (a read by a caller-supplied id leaks the row), and no PY_OWNERSHIP_PATTERNS match. Ownership evidence must tie the object to the authenticated caller: an owner, user, tenant, team, account, customer, org or workspace column compared with or bound to current_user, user, request.user, g.user, principal, identity or caller (either side); an authorization helper (authorize(, can_access(, ensure_owner( and similar); a permission, membership, role, tenancy or scope signal; or a 403 refusal. A name bound from the caller (uid = current_user.id, then owner_id=uid) counts like the caller (pyOwnershipByBoundName(), BUG-069). A 404 and a caller-supplied user_id or org_id no longer count (BUG-030, fixed 2026-11-10).

Both are HIGH, not CRITICAL, by design. The source states the limits: auth applied in another file (include_router(..., dependencies=...), middleware) is invisible; Django class-based views and URLconf routing are not recognized; and the rule finds a handler that never mentions an owner or tenant, it does not prove that a tenant check that is present is correct. guides/tenant-isolation-tests.md covers what a scanner cannot.

Severity, summary and exit code

There are four levels, set per rule and never changed at run time: 19 rules are CRITICAL, 17 HIGH, 8 MEDIUM and 2 LOW. Severity does three things:

  • It orders the human report (CRITICAL first) and sets the icon of each block.
  • It builds the summary line under "AUDIT COMPLETE", for example 0 CRITICAL · 2 HIGH · 1 MEDIUM · 0 LOW.
  • It decides the exit code: with --fail-on-error, any CRITICAL or HIGH finding exits 1. MEDIUM and LOW are reported and never fail a build.

A finding is not weighted by count or by file. One HIGH fails CI the same as fifty.

Suppression

A file can be left out of every rule kind by an otlc-guardian:audit-exempt marker comment line in its first 4 KB, or by a line in security/.audit-allowlist at the project root with a mandatory # reason:; every run prints both lists. The full rules, the allowlist format and its rejection warnings are in chapter 06.

What the tests verify

tests/audit.test.js (run by npm test and npm run test:audit) builds a temporary directory per case, runs the engine on it as a subprocess with --json, and asserts on findings[].rule.id. Run on 2026-11-10 after AGT-002: Passed : 326, Failed : 0, Known : 0. Every rule id appears in at least one test. Since 2026-11-10 a table-driven block gives each rule that had no test one sample it must flag and one it must leave alone. Other blocks cover dependency-directory skipping, the test-file conventions, the CFG-003 bind distinction, the DEP-001 server gate, scan root versus project root, INJ-005b precision both ways, analyzer robustness on malformed files, and the BUG-041 partial-scan cases.

knownBug(bugId, name, fn) runs a test that reproduces an open bug. While the assertion fails it prints (known: BUG-NNN) and counts toward "Known"; the moment it passes, the suite fails with "passes now: BUG-NNN looks fixed. Move this to test() and update BUGS.md." The assertion is never loosened. The two known-bug tests today are DEP-002 on a bare .env (BUG-039) and INJ-001 on retrieval( (BUG-040).

Where the docs and the code disagree

This chapter follows the code. Differences found on 2026-11-10:

  • README.md says to run guardian audit "from anywhere inside a project". The code scans the current directory (or the given target) only; from a subdirectory it audits that subdirectory, with only the allowlist, manifests and absence checks taken from the project root.
  • README.md lists the CI step as guardian audit . --fail-on-error; the workflow runs node security/03-audit.js . --fail-on-error. Same behavior, different entry point.
  • skill/SKILL.md describes project checks as "Missing /health endpoint, committed .env". The committed-.env check could not fire until BUG-039 was fixed (2026-11-10), and WEB-002 is not mentioned.
  • SETUP.md lists the workflow steps as audit, Gitleaks, npm audit, pip-audit. The workflow runs npm test and guardian check before the audit, and the exemption summary step after it.
  • The README and SETUP.md flag descriptions (--fail-on-error exits 1 on CRITICAL or HIGH) match the code. The engine's own header comment ("exit code 1 if issues found") does not.
