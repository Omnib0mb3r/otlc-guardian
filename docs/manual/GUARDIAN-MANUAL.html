Rules an agent reads. Checks it cannot talk its way past.

OTLC Guardian is a security floor for AI-assisted code. This manual explains each part as the code builds it today.

The parts of Guardian, which layer each one defends, where each runs, and the version and release state of 1.5.0.

The audit engine

security/03-audit.js: a static scan of a project's source against 48 rules, run by people, agents and CI before code is committed or shipped.

What the audit is and is not

security/03-audit.js is a standalone Node script (ESM, no dependencies beyond fs and path). It walks a directory, reads source files as text and reports places where the code matches a known bad shape: a hardcoded key, a silent catch, SQL built by concatenation, a route handler that writes to the database without checking who is calling, and so on. It is a review and CI tool. It runs once, prints a report, and exits.

It is not part of a running application. Nothing in it is imported by the runtime guard (security/01-injection-guard.js), the hooks or the SQL helper, and it never executes the code it scans. Its only subprocess is git, for DEP-002. It does not parse JavaScript or Python into a syntax tree: pattern rules are regular expressions, and the analyzers find route handlers by matching signatures and then balancing braces (JavaScript) or reading indentation (Python). A clean result means none of the 42 shapes was found. It does not mean the code is secure, and the analyzers say so in their own comments (see Route-handler analyzers).

The file exports runAudit and AUDIT_RULES, and package.json exposes it as otlc-guardian/audit and as the guardian-audit bin. The CLI entry at the bottom of the file runs only when the file is the program Node was started with (isEntryPoint(), comparing real paths, so a start through npm's bin symlink counts); until 2026-11-10 it also ran on every import (BUG-053). Every test in tests/audit.test.js spawns it as a subprocess instead of importing it.

One run, start to finish

The order inside runAudit():

  1. scanRoot = path.resolve(target); projectRoot = findProjectRoot(scanRoot).
  2. Status header printed: target, project (only when it differs from the target) and the live rule count line.
  3. loadAllowlist(projectRoot).
  4. collectFiles(scanRoot, allExtensions), where allExtensions is the union of every rule's fileTypes.
  5. Each collected file is read once to decide exemption with exemptionMechanism(). File and exempt counts are printed, then every exempt path by mechanism, then each per-rule exemption as [allowlist rule] <path> [IDS].
  6. Pattern rules, in AUDIT_RULES order, over the files whose extension is in the rule's fileTypes.
  7. Analyzer rules, same file filter.
  8. Project rules.
  9. Report, then process.exit(1) if --fail-on-error was given and any finding is CRITICAL or HIGH. Otherwise runAudit() returns the findings array and the process ends with code 0.

Command line

node security/03-audit.js [target] [--json] [--fail-on-error]
guardian audit [target] [--json] [--fail-on-error]

Which files get scanned

collectFiles(rootDir, extensions) builds the list. It is called once from the scan root with the union of all rules' fileTypes, which today is .js .ts .jsx .tsx .mjs .cjs .mts .cts .py .env .json .yaml .yml .html .htm .vue .svelte, plus every file a rule with includePatterns names by path (includedByRule(); today AGT-002's instruction files, below).

  • Extension match. A file is kept when path.extname(name).toLowerCase() is in the list. A name with no extension, such as Dockerfile, is never collected. The one exception is a bare .env (DOTENV_FILE), kept by name for DEP-002 (BUG-039, fixed 2026-11-10). No pattern or analyzer rule reads it, because no fileTypes list contains the empty extension, so the secret rules still never read .env, .env.local or .env.production: a gitignored .env is where secrets belong. The .env entry in SECRET_FILE_EXTS only matches names like prod.env.
  • Path match (BUG-002). A rule with includePatterns reads only the files whose path inside the project, with a leading /, matches one; its fileTypes is unused (appliesTo()). collectFiles(rootDir, extensions, byPath) keeps such a file whatever its extension, so a .md file is collected only when it is an instruction file. A file collected this way is read by its rule alone: collectedByPath() keeps it out of every project check's evidence, because Guardian's own CLAUDE.md asks for a /health endpoint and DEP-001 would read that as the app having one.
  • Skipped directories. SKIP_DIRS is matched against the entry name at any depth: node_modules, bower_components, vendor, venv, .venv, site-packages, dist-packages, dist, build, .next, out, target, __pycache__, .pytest_cache, .mypy_cache, .ruff_cache, .turbo, .cache, coverage, .git. Dependency code is left to npm audit and pip-audit. env is deliberately not on the list because real projects use it for source. Other dot-directories (.github, .claude) are walked, with one exception: .claude/worktrees/, where Claude Code keeps its git worktrees. Each is a second checkout of the same repository, so walking them reported every finding once more per worktree (BUG-081). isClaudeWorktrees() matches the name together with its parent, so a folder that is only named worktrees is still read, and a worktree given as the target is audited.
  • Symlinks. The walker uses readdirSync(..., { withFileTypes: true }) and only follows entries whose isDirectory() or isFile() is true. A symlink reports neither, so symlinked files and directories are skipped.
  • Unreadable directories are skipped silently (the readdirSync error is caught and the directory contributes nothing). Unreadable files are skipped by each pass the same way.
  • Single-file target. If the target is a file, collectFiles() returns [target] when its extension is wanted and [] otherwise. Before BUG-041 it called readdirSync on the file, failed, and scanned nothing. The source comment names the use case: a commit hook auditing changed files.
  • Missing target. statSync(..., { throwIfNoEntry: false }) returns nothing, the walk's readdirSync fails, and the list is empty. The run reports 0 files and no issues.

Scan root and project root

Two directories matter, and since 1.3.1 (BUG-018) they are kept apart:

  • scanRoot: the target the user named. The walker collects files only from here, and report paths are relative to it.
  • projectRoot: found by findProjectRoot(), which walks upward from the scan root (at most 8 levels) and stops at the first directory holding any of .git, security/.audit-allowlist, package.json, requirements.txt, pyproject.toml, Pipfile. With no marker anywhere it falls back to the scan root.

The project root is used for three things: the central allowlist (loadAllowlist(projectRoot), and allowlist entries are matched as paths relative to it), the manifests that DEP-001's looksLikeHttpServer() reads, and the evidence for project checks that prove an absence. That last point is BUG-041 (fixed 2026-11-10): a project check declares evidence: "project" when its finding means "nowhere in the project". On a partial scan (projectRoot !== scanRoot) such a check receives collectFiles(projectRoot, allExtensions), computed once and shared, and its finding names the project root. DEP-001 and WEB-002 carry the flag. DEP-002 is a presence check (a .env exists), so it keeps the scanned files: a hit there is true of the part the user asked about. Before the fix, auditing DevNeural's 07-daemon/src/capture/hooks reported DEP-001 although DevNeural serves GET /health elsewhere in the repo.

The scan does not widen to the project

Running the audit from a subdirectory scans that subdirectory only. Pattern and analyzer rules never look outside the scan root. Only the absence checks and the manifest lookup see the whole project.

The analyzer kind exists because missing authentication and IDOR are absences inside a block ("nowhere in this handler is there an auth check"), and a regular expression cannot express that across arbitrarily nested braces. Exemptions and project checks (BUG-059): an absence check (evidence: "project", DEP-001 and WEB-002) reads exempt files too, so an exempt file can still provide the "health" evidence for DEP-001 or a CSP for WEB-002; a presence check (DEP-002) leaves exempt files out. Route-handler analyzers

JavaScript and TypeScript (AUTHZ-001, AUTHZ-003, VAL-001)

findRouteHandlers(content) finds handlers by four signatures in HANDLER_SIGNATURES:

  • app|router|server|api .get|post|put|patch|delete|all( (Express, Fastify, Hono style). lastInlineHandler() takes the inline function (=> { or function (...) {) whose block is the call's last argument, within 40,000 characters; everything before it in the call is the handler's head (path and route-level middleware). A handler passed by name has no block there and is skipped. Before BUG-070 (fixed 2026-11-10) the body was the first { after the signature, so an options object in middleware (passport.authenticate("jwt", { session: false })) was read as the handler.
  • export [async] function GET|POST|PUT|PATCH|DELETE( (Next.js App Router).
  • export const GET|POST|... = [async] ( (App Router, arrow form).
  • export default [async] function name( (Pages Router, Vercel).

Severity, summary and exit code

There are four levels, set per rule and never changed at run time: 19 rules are CRITICAL, 19 HIGH, 8 MEDIUM and 2 LOW. Severity does three things:

  • It orders the human report (CRITICAL first) and sets the icon of each block.
  • It builds the summary line under "AUDIT COMPLETE", for example 0 CRITICAL · 2 HIGH · 1 MEDIUM · 0 LOW.
  • It decides the exit code: with --fail-on-error, any CRITICAL or HIGH finding exits 1. MEDIUM and LOW are reported and never fail a build.

A finding is not weighted by count or by file. One HIGH fails CI the same as fifty.

The runtime guard and helpers

The injection and secret scanner every other layer calls, its Python port, and the server and SQL helpers that ship beside it.

The runtime layer is four files in security/. 01-injection-guard.js is the scanner: it reads a string, normalizes it, runs 28 injection rules and 16 secret rules over every decoded view, and returns the findings. injection_guard.py is its Python port. 02-code-security.js holds Express helpers (headers, request ids, a logger, a rate limiter, error shapes, a health route). 04-sql-guard.js is a tagged-template SQL helper that turns every interpolation into a bound parameter. Nothing in the layer has a dependency outside the Node or Python standard library.

This chapter describes the code at git 0fa32ce plus the 1.5.0 working tree (unreleased). Where the README, SECURITY.md or SETUP.md say something different, the code wins and the gap is listed in Code versus docs.

Every pattern is a single regex or a linear comment walker, and every normalizer pass is linear in its input, so the cap is a memory bound rather than a guard against slow regexes (comment above MAX_SCAN_LENGTH). Each rule reports at most once per call: scan() keeps the first match only.

The comment walker (027, 028)

These two rules carry a match and a matchAll built by commentMatcher(open, close) instead of a regex. scanChange(): judging what a change adds

scanChange(before, after, mode) answers "does this edit add a finding", which a whole-file scan() cannot: a file that already quotes a pattern (a security document, Guardian's own CLAUDE.md section) would be flagged on every edit, and judging by rule id alone would let a second copy of an already-present rule through. The PreToolUse hook calls it for every Write, Edit and MultiEdit it judges (chapter 04).

Steps

  1. A non-string after returns an empty result. A non-string before is treated as "" (a new file, judged in full).
  2. changedWindows() trims the common prefix and common suffix (compared by UTF-16 code unit) but keeps up to 2048 characters of each on both sides. The result is an old window and a new window. A small edit to a large file costs a small scan, and a payload appended past the 1 MB mark of the whole file is still inside the new window.
  3. scan(newWindow, mode) lists the candidate findings.
  4. scanViews() runs on both windows (each capped at 1,000,000).
  5. Each candidate is kept or dropped:
    • GUARD-INJ-OVERSIZE is always kept: unscanned text is never "already accounted for".
    • GUARD-INJ-UNICODE is kept when the new window holds more detect-set characters than the old one.
    • Every other rule goes through firstAddedMatch(): for each view index, the rule's matched strings in the old view are counted into a multiset, then the new view's matches consume those counts. The first match with no count left is the added one. For an injection finding matched is replaced with that new string; a secret finding keeps its redaction.
  6. The return is { violations, hasSecrets, hasCritical } over the kept findings only.

What this gives (each case has a test in tests/injection-guard.test.js, group "scanChange()"): rewriting a file that already quotes a pattern is clean; adding a second copy is a finding; swapping the quoted example for a different payload is a finding; a payload completed across old and new text is a finding; an encoded copy of a quoted pattern is a finding (it is a new string in a decoded view); removing a pattern is never a finding.

Known limits

  • Moving is not adding (BUG-042, fix staged in staging/, not yet live). The judgement is a count. Cutting an already-quoted pattern out of a data context (an example block) and pasting it into a live instruction in the same window leaves every count unchanged, so nothing is reported. The staged fix classifies matches only in the views that keep lines in place, so a payload obfuscated with markdown (ig**no**re ...) or written as base64 can still be moved out of a fence silently (re-probe 2, S7; documented, not fixed).
  • The window can be crossed (BUG-046, fix staged in staging/, not yet live). The multi-word rules allow any run of whitespace between words. If the existing half of a phrase sits more than 2048 characters of whitespace away from the added half, the window cuts the old half off and neither window holds the whole match.
  • A new window over 1,000,000 characters always yields GUARD-INJ-OVERSIZE (MEDIUM), which the hook treats as advisory.

Behavior

  • Every interpolation becomes one placeholder and one entry in values, whatever it is: strings, numbers, 0, "", null, undefined, objects, buffers. An array is one value, not a list; an IN list needs the driver's own form (for example = ANY(${arr}) on postgres).
  • A nested sql`...` result is inlined; placeholders are renumbered and values concatenated in document order, in the outer tag's dialect.
  • The result carries toPostgres(), toMysql(), toSqlite(), which re-render the stored parts without mutating the original. The parts sit under a non-enumerable Symbol key, so spreading or JSON.stringify does not expose them, and a user object cannot pass itself off as a query.
  • Text between interpolations is kept byte for byte.

What it refuses (all throw Error)

  • createSqlHelper() with any driver outside the three.
  • sql.identifier() when the allow-list is not a non-empty array.
  • sql.identifier() when the name is not a string matching ^[A-Za-z_][A-Za-z0-9_]*(\.[A-Za-z_][A-Za-z0-9_]*)?$ (an optional single schema. prefix). This check runs before the allow-list check, so a bad name is rejected even if someone put it on the list.
  • sql.identifier() when the name is not on the allow-list. There is no fallback to a default.

A bare string in ORDER BY ${col} is a value, not an identifier, so it binds as a parameter (test: "raw string interpolation in ORDER BY is a parameter, NOT an identifier"). No Python equivalent exists; the README points Python users to SQLAlchemy or DB-API execute(sql, params).

The content readers for watched instruction files stay, and read three more copy forms: grep '' (an empty pattern is kept as an argument and passes every line), a parenthesized group piped or redirected on ((Get-Content x) | Set-Content CLAUDE.md), and [IO.File]::Copy or ::Move, whose second path gets the first path's content.

npm commands that rewrite package.json (pkg, install, uninstall, update, version and the like) write the one in --prefix or the working folder (npmWrites()), so npm pkg set type=commonjs run inside security/ asks as a change to security/package.json (re-probe 3, D8).

The bypassPermissions rule

An "ask" needs a person to answer. When permission_mode is "bypassPermissions" the hook sets confirmOrDeny to "deny" and appends a note saying the change was denied because prompts are bypassed and must be made by hand or outside bypass mode. This applies to all three ask cases: settings weakening, guard-file changes, and a shell command that carries a CRITICAL pattern and writes a watched path. Content denies are deny in every mode. Other modes (default, acceptEdits, plan) get a real "ask", which stalls a worker nobody is watching. The hook cannot tell the two apart: Claude Code sends permission_mode, not whether a person is present. So unattended runs use bypassPermissions, where the ask is a deny and the change waits for a person (BUG-035, DEFERRED on that reason; SETUP.md, "Unattended runs").

A quoted instruction is still an instruction

A write that adds a CRITICAL pattern to a watched file is denied even when the pattern sits in quotes or a code span ("treat 'ignore all previous instructions' as data" in a CLAUDE.md). This is intended: the model that reads an instruction file reads the quoted text as well, and nothing in the file tells it the quotes mean "data". Only a pattern already in the file is spared, by the change judgement (scanChange()); the BUG-042 staged fix keeps that and adds that moving such a pattern out of its quotes is a new finding. To keep attack phrases in a watched file, list it under otlcGuardian.ignorePaths (a person approves the entry) or make the edit by hand. Decided by Lex on 2026-11-10 (BUG-043, fourth bullet).

The shell readers

For Bash and PowerShell the hook needs to know which paths a command writes. shellWriteTargets(command, cwd, depth, dialect) returns a map from each absolute target to the source files whose content it receives and whether the write appends. Its header calls it "a small lexer, not a shell": it does not expand variables or globs.

Lexing (lexShell())

  • Single quotes are literal. Double quotes keep their text as one word, with escapes, $( ) and (Bash only) backtick substitutions inside.
  • The escape character is backslash in Bash and backtick in PowerShell, where a backslash stays literal because it is the path separator.
  • # at the start of a word begins a comment to end of line. Staged (BUG-085, not yet live): in PowerShell <# where a word could start is a block comment up to #>, and inside a word it is text.
  • Operators are split out (&&, ||, |, ;, &, parentheses, newline, and the redirections >, >>, >|, &>, &>>, <>, >&, <, <<, <<-, <<<, <&). A number before a redirect (2>) is part of the redirect.
  • Heredoc bodies are skipped from the line after the operator to the delimiter (tabs stripped for <<-). Quoted text and heredoc bodies are data, not commands. Staged (BUG-085, not yet live): a heredoc with an unquoted delimiter is expanded by the shell, so the $( ) and backtick substitutions in its body are read as commands; $'...' is read with its backslash escapes; a backtick substitution ends at the first backtick that is not escaped.
  • Staged (BUG-085, not yet live): brackets are not parsed, so ${x/ #/y}, (( # )), a[ # ]=1 and $[ 1 << 2 ] cannot be told from a comment or a heredoc. When a comment or a heredoc body is left out while ${, [, (( or a ( stuck to a word is open, or a double-quoted string ends inside ${ }, lexShell() returns uncertain: true. onlyReads() is then false, bareWordText() blanks nothing, and a command that names a watched path asks.
  • The text of each $( ) and backtick substitution is collected and read again as a command, to a depth of MAX_SHELL_DEPTH (4).

Install and update

How guardian init puts Guardian into a project, how guardian update keeps it current, and how to take it out again by hand.

The CLI is one file, bin/guardian.js, with no dependencies. It installs Guardian into a project by copying and merging files from its own source directory, and it never deletes anything. This chapter covers each command, what init writes where, how update differs from it, and how a project is taken back out. Everything here comes from bin/guardian.js at git HEAD 0fa32ce (1.5.0, unreleased).

The package and the source directory

package.json declares two executables: guardian (bin/guardian.js) and guardian-audit (security/03-audit.js run directly). It requires Node 22 or later (engines.node is >=22.0.0), has empty dependencies and devDependencies, and exports four modules: . (the injection guard), ./security, ./audit and ./sql. The files list ships bin/, security/, guides/, skill/, .claude/, .github/, the behavior and doc files, .env.example and .gitleaks.toml. tests/ is not in it.

The marker block in the behavior files

mergeMd() handles all four Markdown files. Guardian's section always sits between <!-- OTLC-GUARDIAN-START --> and <!-- OTLC-GUARDIAN-END -->, followed by a --- rule and three comment lines saying not to edit inside the markers. The content is the matching file from ROOT, trimmed.

  1. File missing. A new file is written with the marker block at the top and nothing above it. Since 1.1.1 a new file is sealed with markers too, so a second init is a no-op rather than a second append.
  2. File present, no start marker. Your content is kept with trailing whitespace trimmed, then one blank line, then the block.
  3. Start marker present. init prints Guardian section already present, skipping and leaves the file alone.

The test is existing.includes(marker): a file that contains the start marker anywhere, for example in a quoted example, counts as already merged.

.gitignore and .env.example use the shell-comment pair # OTLC-GUARDIAN-START / # OTLC-GUARDIAN-END. mergeGitignore() compares path tokens after removing an inline # comment (gitignorePathToken()), so your .env # local secrets line covers Guardian's .env. mergeEnvExample() compares keys (the text before =), so your value for a key is never joined by Guardian's. Comment lines from Guardian's templates are dropped. If nothing is missing, no block is written. A whole-file copy (the file was missing) has no markers.

What init never overwrites

init overwrites nothing. Every existing file is either merged or skipped. In detail:

  • Your text in the four behavior files, .gitignore and .env.example is never changed or removed. Only a block is appended, and only once.
  • Your hooks in .claude/settings.json are never removed or edited. The one exception is the migration step, which moves Guardian's own command entry out of a block with a different matcher; it can also drop a block that held only that entry.
  • Every existing file under security/, .claude/hooks/ and .github/ is skipped, including an old Guardian scanner or hook. Before 1.5.0 this was also true of update, which is BUG-025.
  • Files Guardian never creates (.cursorrules, .windsurfrules, .aider.conf.yml, copilot-instructions.md) are never written. The hook scans them; the CLI does not touch them.

Update and the PreToolUse hook

The PreToolUse hook (chapter 04) protects the two hook scripts and security/01-injection-guard.js: any change by a file tool, or a Bash or PowerShell command whose write target is one of them or a folder holding one, asks for confirmation, and is denied in bypass mode. guardian update writes those files with copyFileSync() from its own Node process. The hook sees tool calls, not file system writes, so it never sees these writes. If an agent runs guardian update through Bash, the command text spells out no write target for the hook to read, so that is not caught either.

SETUP.md's advice follows from this: run update yourself. What it writes is limited to the content of ROOT, so the real question is who can change the Guardian source directory. That repo's own hook protects its own copies of the hook files and scanner.

  • No # at all: .audit-allowlist:N missing reason, line ignored.
  • Text after the # does not start with reason: (case-insensitive): reason must start with "reason:", line ignored.
  • # reason: with nothing (or only spaces) after it: reason is empty, line ignored (BUG-056, fixed 2026-11-10; before the fix the prefix alone was accepted).
  • A path that itself contains # cannot be listed, because the split happens at the first #.

Per-rule entries

A rule list in brackets between the path and the # limits the entry to those rules, the way eslint-disable <rule> or nosemgrep: <rule-id> does. Prefer it to a whole-file entry: a file exempted for one sink should not lose every other check.

src/components/ui/chart.jsx  [INJ-003]           # reason: stock shadcn ChartStyle; ChartConfig and id are developer constants
src/legacy/report.js         [ERR-003, CFG-001]   # reason: CLI report script, output is its purpose
  • ALLOWLIST_RULE_LIST takes the list only when it is the last thing before the # and follows whitespace, so a path with brackets (app/docs/[id]/page.jsx) stays a path.
  • parseAllowlistRules() resolves each id against AUDIT_RULES, in any case. An unknown id (a typo, or a runtime GUARD- id): unknown rule id "X", line ignored. An empty list: empty rule list, line ignored. An absence check (DEP-001, WEB-002): ... is a project check and cannot be suppressed per file, line ignored, because an exemption never hides a file as evidence (BUG-059). A rejected line suppresses nothing.
  • The reason rules above apply unchanged, the BUG-056 empty-reason check included.
  • Several lines for one path merge: rule lists add up, and a whole-file entry wins over a per-rule one.

shadcn chart.jsx and INJ-003

Every project that adds the shadcn chart component gets one INJ-003 (HIGH) finding in components/ui/chart.jsx (or .tsx). The finding is right. Only THEMES in that file is a constant: ChartStyle writes the id prop and every colour in the config prop into a <style> element through dangerouslySetInnerHTML, unescaped.

Server-render risk

React does not escape dangerouslySetInnerHTML content when it renders on the server. In a server-rendered app (Next.js), a ChartConfig colour or an id holding </style><script>... closes the style tag and runs as script, and any value can inject CSS. That matters when chart config is built from user data, such as user-chosen dashboard colours or a stored theme. The audit reads one file at a time and cannot see where the config comes from, so it keeps reporting the sink.

Once you have checked that ChartConfig and id are developer constants in your app, record that decision with a per-rule entry, which keeps every other rule running on the file:

src/components/ui/chart.jsx  [INJ-003]  # reason: stock shadcn ChartStyle; ChartConfig and id are developer constants, never user input

Do not use a whole-file entry for it, and re-check the line if you change the component or start building chart config from user data. Guardian has no built-in exemption for the component (BUG-003, resolved 2026-11-10: a path skip or fingerprint would hide the sink in the apps where it is live).

Both warnings go to stderr through console.warn. The path is stored with backslashes turned into forward slashes. Nothing else is normalized.

exemptionMechanism() takes each scanned file's path relative to the project root, with forward slashes, and looks it up in the map. The match is exact:

  • no globs and no directory entries: tests/ exempts nothing;
  • no ./ prefix: ./bin/guardian.js never matches;
  • case-sensitive on every platform, Windows included, because it is a Map lookup.

The project root comes from findProjectRoot(). It walks up from the scan target, at most 8 levels, and stops at the first directory that holds any of .git, security/.audit-allowlist, package.json, requirements.txt, pyproject.toml or Pipfile. Since 1.3.1 a subdirectory scan therefore still reads the root allowlist (BUG-018). It also means a scan of a subpackage with its own package.json stops there and does not read an allowlist further up.

The audit-exempt marker

AUDIT_EXEMPT_MARKER is otlc-guardian:audit-exempt. exemptionMechanism() tests MARKER_LINE against the first 4096 characters (MARKER_WINDOW, the "4 KB" of the docs). The marker counts only on a line of its own that starts with a comment opener: //, #, /*, a JSDoc *, <!-- or --, optionally indented. It must end as a whole word; a reason, */ or --> may follow. A string, a regex, a backquoted mention, prose that names the marker, or the marker trailing code on the same line does not exempt the file (BUG-057, fixed 2026-11-10; before the fix any occurrence counted).

// otlc-guardian:audit-exempt  legacy route, tracked in BUGS.md

Before the fix, bin/guardian.js (line 9) and security/03-audit.js (line 22) were exempt by marker only because their header comments name it, and this chapter was exempt because it quotes the example above. Now the repo audit reports 0 marker exemptions; the two scripts are exempt through their allowlist lines.

The allowlist is checked first. A file that qualifies both ways is reported as [allowlist], the mechanism with a written reason. Neither mechanism is per rule: an exempt file is skipped by every pattern rule (scanFile() checks exemptPaths) and every analyzer rule (the fileCheckFn loop does the same, verified by the test "audit-exempt marker suppresses analyzer rules too" in tests/audit.test.js).

What an audit exemption does not cover

The three project checks (DEP-001, DEP-002, WEB-002) are checkFn rules. The rule, decided under BUG-059 (2026-11-10): an exemption silences findings about a file, and never hides the file as evidence.

  • Absence checks (evidence: "project": DEP-001 no health route, WEB-002 no CSP) get every file, exempt or not, or the project root's files on a partial scan (BUG-041). A health route in an exempt file still satisfies DEP-001; a CSP header in an exempt file still clears WEB-002. No exemption removes their finding: the finding is about the whole project, so the fix is in the project.
  • Presence checks (DEP-002, a committed .env) get the scanned files minus exemptPaths. The finding is about the file itself, so an allowlist line such as .env # reason: committed defaults, no secrets silences it, and the file shows in the [allowlist] list like any other.

Hook exemption: otlcGuardian.ignorePaths

Since 1.5.0 this is the only exemption the PreToolUse hook honors. It is set in the project's .claude/settings.json:

{ "otlcGuardian": { "ignorePaths": [".planning/specs/injection-defense.md"] } }

How it matches

isIgnoredPath() canonicalizes the target with canonicalPath(): forward slashes, . and .. collapsed, any NTFS stream suffix removed. It then checks whether the result contains each entry, with backslashes in the entry turned into slashes. It is a substring match, so docs exempts every path with docs anywhere in it, and spec.md also exempts old-spec.md (BUG-058, (fix staged in staging/, not yet live): the staged hook resolves each entry from the project root and exempts only that file or that folder's contents; an entry relying on the substring reading must then be written in full). The match ignores case on Windows and macOS only (CASE_INSENSITIVE_FS), so an entry never covers a different file on a case-sensitive file system. Since 1.5.0, empty strings and non-strings are skipped; an empty entry used to match every path and switch the hook off.

Where it is read

loadSettings() reads only <projectRoot>/.claude/settings.json. The root is CLAUDE_PROJECT_DIR, then the payload's cwd, then process.cwd(). An otlcGuardian block in settings.local.json has no effect. If settings.json does not parse, the hook warns on stderr and uses no exemptions and the default watch list, so a broken file never widens what is skipped.

What it covers

The hook applies it in one place, isWatched = t && !isIgnoredPath(t, settings) && isWatchedPath(t, settings). An ignored path drops out of the content verdicts for that path: the deny for a CRITICAL pattern a file write adds, the deny for content a shell command copies in, the ask for a Bash command, and the advisories. It does not cover the two self-protection checks, which run earlier and never consult it. A change that weakens .claude/settings*.json, and any change to the hook scripts or security/01-injection-guard.js, still asks even when an ignorePaths entry names that file.

The audit reads the same entries for the rules marked honorsIgnorePaths (today AGT-002): guardianIgnorePaths() reads otlcGuardian.ignorePaths from the project root's .claude/settings.json, and ignoredByGuardian() matches as the staged hook does, a path from the project root covering that file or folder, any case on Windows and macOS; an entry naming the root or a folder above it covers nothing. A settings file that cannot be read adds no entry. Each skipped file becomes a per-rule exemption and is printed as [ignorePaths] <path> [AGT-002], so the exemption is never silent.

Who may add an entry

A person. settingsWeakening() compares the settings before and after a Write, Edit or MultiEdit, and lists otlcGuardian.ignorePaths gains N entries as a weakening whenever an entry appears that was not there before; swapping one entry for another counts. The decision is ask, or deny when the session runs in bypassPermissions mode. A Bash or PowerShell command that writes, moves or removes a settings file, or a folder that holds one, is asked about every time, because the hook cannot see the result. Removing an entry is not a weakening, so the settings check does not flag it.

Settings that narrow the hook

These are not exemptions, but they shrink what the hook watches, and the same check guards them:

  • extendDefaults: false replaces the default watch list with watchPaths alone. Turning it off asks: "default watch list dropped".
  • Removing an entry from watchPaths asks: "watchPaths loses N entries".
  • disableAllHooks: true in either settings file, removing a Guardian hook, changing its matcher or command, or lowering its timeout asks. The hook reads settings.json and settings.local.json together for these, as Claude Code merges them.

guardian list-watched prints the effective list: defaults on or off, custom watch paths, ignored paths. It ends with the line "Exemptions: only otlcGuardian.ignorePaths in .claude/settings.json. The hook asks before an agent adds one."

When to use one

Use an exemption only when the finding is wrong, and only in a way a reviewer can see. That is Step 3 of the OTLC-Guardian skill: "Never suppress a finding because the fix is inconvenient." For the audit that means an allowlist line with a real reason, per rule wherever the finding concerns one sink; it is preferred over the marker because it is one reviewable line in one file, takes precedence, and carries a written justification. Anyone with write access can add either, an agent included, because the hook does not watch security/.audit-allowlist or source files. The safeguards are the reason field, the exempt summary on every run, and CODEOWNERS review where it is set up. For the hook, the person approving the prompt decides.

Known-bug tests are not suppression. When a rule gets a case wrong, the case is logged in BUGS.md and kept as a knownBug() test in tests/audit.test.js, which fails the suite once the bug stops reproducing. The rule is never loosened to make the case pass.
