06

Exemptions and suppression

Every way to keep a file out of the audit or the PreToolUse hook, where each one is reported, and what stops it from being abused.

The audit and the hooks have separate exemptions. The one crossing is AGT-002: the audit rule for instruction files honors the hook's otlcGuardian.ignorePaths too, so a file a project keeps out of the hook is not reported by the audit either; the hook never honors the audit's. The audit (chapter 02) skips whole files listed in a central allowlist or carrying a per-file marker. The PreToolUse hook (chapter 04) skips paths listed in otlcGuardian.ignorePaths. The web content hook and the runtime guard have no exemption at all. This chapter covers each mechanism from the code: loadAllowlist(), exemptionMechanism() and runAudit() in security/03-audit.js, and loadSettings(), isIgnoredPath() and settingsWeakening() in .claude/hooks/injection-guard-hook.mjs.

The central allowlist

loadAllowlist(rootDir) reads <projectRoot>/security/.audit-allowlist. If the file is missing or unreadable it returns an empty list without a warning. Each line is trimmed. Blank lines and lines that start with # are skipped. Every other line is split at its first #:

bin/guardian.js                    # reason: CLI tool, console.* output is its purpose
  • No # at all: .audit-allowlist:N missing reason, line ignored.
  • Text after the # does not start with reason: (case-insensitive): reason must start with "reason:", line ignored.
  • # reason: with nothing (or only spaces) after it: reason is empty, line ignored (BUG-056, fixed 2026-11-10; before the fix the prefix alone was accepted).
  • A path that itself contains # cannot be listed, because the split happens at the first #.

Per-rule entries

A rule list in brackets between the path and the # limits the entry to those rules, the way eslint-disable <rule> or nosemgrep: <rule-id> does. Prefer it to a whole-file entry: a file exempted for one sink should not lose every other check.

src/components/ui/chart.jsx  [INJ-003]           # reason: stock shadcn ChartStyle; ChartConfig and id are developer constants
src/legacy/report.js         [ERR-003, CFG-001]   # reason: CLI report script, output is its purpose
  • ALLOWLIST_RULE_LIST takes the list only when it is the last thing before the # and follows whitespace, so a path with brackets (app/docs/[id]/page.jsx) stays a path.
  • parseAllowlistRules() resolves each id against AUDIT_RULES, in any case. An unknown id (a typo, or a runtime GUARD- id): unknown rule id "X", line ignored. An empty list: empty rule list, line ignored. An absence check (DEP-001, WEB-002): ... is a project check and cannot be suppressed per file, line ignored, because an exemption never hides a file as evidence (BUG-059). A rejected line suppresses nothing.
  • The reason rules above apply unchanged, the BUG-056 empty-reason check included.
  • Several lines for one path merge: rule lists add up, and a whole-file entry wins over a per-rule one.

shadcn chart.jsx and INJ-003

Every project that adds the shadcn chart component gets one INJ-003 (HIGH) finding in components/ui/chart.jsx (or .tsx). The finding is right. Only THEMES in that file is a constant: ChartStyle writes the id prop and every colour in the config prop into a <style> element through dangerouslySetInnerHTML, unescaped.

Server-render risk

React does not escape dangerouslySetInnerHTML content when it renders on the server. In a server-rendered app (Next.js), a ChartConfig colour or an id holding </style><script>... closes the style tag and runs as script, and any value can inject CSS. That matters when chart config is built from user data, such as user-chosen dashboard colours or a stored theme. The audit reads one file at a time and cannot see where the config comes from, so it keeps reporting the sink.

Once you have checked that ChartConfig and id are developer constants in your app, record that decision with a per-rule entry, which keeps every other rule running on the file:

src/components/ui/chart.jsx  [INJ-003]  # reason: stock shadcn ChartStyle; ChartConfig and id are developer constants, never user input

Do not use a whole-file entry for it, and re-check the line if you change the component or start building chart config from user data. Guardian has no built-in exemption for the component (BUG-003, resolved 2026-11-10: a path skip or fingerprint would hide the sink in the apps where it is live).

Both warnings go to stderr through console.warn. The path is stored with backslashes turned into forward slashes. Nothing else is normalized.

exemptionMechanism() takes each scanned file's path relative to the project root, with forward slashes, and looks it up in the map. The match is exact:

  • no globs and no directory entries: tests/ exempts nothing;
  • no ./ prefix: ./bin/guardian.js never matches;
  • case-sensitive on every platform, Windows included, because it is a Map lookup.

The project root comes from findProjectRoot(). It walks up from the scan target, at most 8 levels, and stops at the first directory that holds any of .git, security/.audit-allowlist, package.json, requirements.txt, pyproject.toml or Pipfile. Since 1.3.1 a subdirectory scan therefore still reads the root allowlist (BUG-018). It also means a scan of a subpackage with its own package.json stops there and does not read an allowlist further up.

The audit-exempt marker

AUDIT_EXEMPT_MARKER is otlc-guardian:audit-exempt. exemptionMechanism() tests MARKER_LINE against the first 4096 characters (MARKER_WINDOW, the "4 KB" of the docs). The marker counts only on a line of its own that starts with a comment opener: //, #, /*, a JSDoc *, <!-- or --, optionally indented. It must end as a whole word; a reason, */ or --> may follow. A string, a regex, a backquoted mention, prose that names the marker, or the marker trailing code on the same line does not exempt the file (BUG-057, fixed 2026-11-10; before the fix any occurrence counted).

// otlc-guardian:audit-exempt  legacy route, tracked in BUGS.md

Before the fix, bin/guardian.js (line 9) and security/03-audit.js (line 22) were exempt by marker only because their header comments name it, and this chapter was exempt because it quotes the example above. Now the repo audit reports 0 marker exemptions; the two scripts are exempt through their allowlist lines.

The allowlist is checked first. A file that qualifies both ways is reported as [allowlist], the mechanism with a written reason. Neither mechanism is per rule: an exempt file is skipped by every pattern rule (scanFile() checks exemptPaths) and every analyzer rule (the fileCheckFn loop does the same, verified by the test "audit-exempt marker suppresses analyzer rules too" in tests/audit.test.js).

Where audit exemptions are reported

runAudit() works out every exemption before any rule runs and prints the result in the header of every run, whether or not anything was found:

    Files   : 12 scanned
    Exempt  : 3 (0 marker, 3 allowlist)
    [allowlist] security/02-code-security.js, security/03-audit.js, security/04-sql-guard.js

Per-rule entries are counted after the whole-file ones (Exempt : 3 (0 marker, 3 allowlist), 1 with per-rule exemptions) and listed one per line as [allowlist rule] src/components/ui/chart.jsx [INJ-003]. Those files are not in the exempt total: they are still scanned.

That is the output of a fresh guardian init project on 2026-11-10. The listed paths are relative to the scan target. In human mode these lines go to stdout. With --json they go to stderr, and the JSON on stdout carries exempt: { total, marker: [...], allowlist: [...], rules: [{ file, rules: [...] }] }.

The copied CI workflow (.github/workflows/security-audit.yml, step "Audit exemption visibility") runs the audit with --json and writes Files exempted from scanning: N and Files with per-rule exemptions: N to the GitHub step summary. It reports the count and does not fail the build when the count grows. The allowlist header says the same since the 1.5.0 fix; it used to claim CI failed.

What an audit exemption does not cover

The three project checks (DEP-001, DEP-002, WEB-002) are checkFn rules. The rule, decided under BUG-059 (2026-11-10): an exemption silences findings about a file, and never hides the file as evidence.

  • Absence checks (evidence: "project": DEP-001 no health route, WEB-002 no CSP) get every file, exempt or not, or the project root's files on a partial scan (BUG-041). A health route in an exempt file still satisfies DEP-001; a CSP header in an exempt file still clears WEB-002. No exemption removes their finding: the finding is about the whole project, so the fix is in the project.
  • Presence checks (DEP-002, a committed .env) get the scanned files minus exemptPaths. The finding is about the file itself, so an allowlist line such as .env # reason: committed defaults, no secrets silences it, and the file shows in the [allowlist] list like any other.

Built-in rule scope

Some rules leave out code by design. These are part of each rule's definition, not a setting, and the exempt summary does not report them.

Some rules also carry a narrowing inside the regex, such as the (?<!\bsql) lookbehind in INJ-005b that clears the sql tagged template from 04-sql-guard.js. That is part of what the rule detects and cannot be switched off.

Text that silences a rule (a defect)

WEB-002 fires when the project ships an nginx server block and nothing sets a Content-Security-Policy. nginxWithoutCsp() decides "something sets one" with CSP_ANYWHERE, a regex that matches the text content-security-policy (or helmet(, Talisman(, django-csp and others) anywhere in any scanned file or nginx config. A comment that only names the header, a TODO or a doc string, clears the finding. This is not a designed suppression and it shows up nowhere. It is logged as part of BUG-038 (OPEN).

SECURITY.md says: "If you find a way to add an exemption that does not show up in the summary or the allowlist, that is a Guardian security issue." By that standard this defect counts as one.

No other rule has an inline suppression comment. The comment on INJ-005b says "the global doc-exempt marker otlc-guardian:doc plus the per-file otlc-guardian:audit-exempt marker both already short-circuit it at the scanner layer". The audit has no code for otlc-guardian:doc; that comment is stale. Only audit-exempt works in the audit.

Until 2026-11-10 (BUG-060) it copied all seven, and the four bin/ and tests/ lines exempted whatever a project kept at those paths.

Hook exemption: otlcGuardian.ignorePaths

Since 1.5.0 this is the only exemption the PreToolUse hook honors. It is set in the project's .claude/settings.json:

{ "otlcGuardian": { "ignorePaths": [".planning/specs/injection-defense.md"] } }

How it matches

isIgnoredPath() canonicalizes the target with canonicalPath(): forward slashes, . and .. collapsed, any NTFS stream suffix removed. It then checks whether the result contains each entry, with backslashes in the entry turned into slashes. It is a substring match, so docs exempts every path with docs anywhere in it, and spec.md also exempts old-spec.md (BUG-058, (fix staged in staging/, not yet live): the staged hook resolves each entry from the project root and exempts only that file or that folder's contents; an entry relying on the substring reading must then be written in full). The match ignores case on Windows and macOS only (CASE_INSENSITIVE_FS), so an entry never covers a different file on a case-sensitive file system. Since 1.5.0, empty strings and non-strings are skipped; an empty entry used to match every path and switch the hook off.

Where it is read

loadSettings() reads only <projectRoot>/.claude/settings.json. The root is CLAUDE_PROJECT_DIR, then the payload's cwd, then process.cwd(). An otlcGuardian block in settings.local.json has no effect. If settings.json does not parse, the hook warns on stderr and uses no exemptions and the default watch list, so a broken file never widens what is skipped.

What it covers

The hook applies it in one place, isWatched = t && !isIgnoredPath(t, settings) && isWatchedPath(t, settings). An ignored path drops out of the content verdicts for that path: the deny for a CRITICAL pattern a file write adds, the deny for content a shell command copies in, the ask for a Bash command, and the advisories. It does not cover the two self-protection checks, which run earlier and never consult it. A change that weakens .claude/settings*.json, and any change to the hook scripts or security/01-injection-guard.js, still asks even when an ignorePaths entry names that file.

The audit reads the same entries for the rules marked honorsIgnorePaths (today AGT-002): guardianIgnorePaths() reads otlcGuardian.ignorePaths from the project root's .claude/settings.json, and ignoredByGuardian() matches as the staged hook does, a path from the project root covering that file or folder, any case on Windows and macOS; an entry naming the root or a folder above it covers nothing. A settings file that cannot be read adds no entry. Each skipped file becomes a per-rule exemption and is printed as [ignorePaths] <path> [AGT-002], so the exemption is never silent.

Who may add an entry

A person. settingsWeakening() compares the settings before and after a Write, Edit or MultiEdit, and lists otlcGuardian.ignorePaths gains N entries as a weakening whenever an entry appears that was not there before; swapping one entry for another counts. The decision is ask, or deny when the session runs in bypassPermissions mode. A Bash or PowerShell command that writes, moves or removes a settings file, or a folder that holds one, is asked about every time, because the hook cannot see the result. Removing an entry is not a weakening, so the settings check does not flag it.

Settings that narrow the hook

These are not exemptions, but they shrink what the hook watches, and the same check guards them:

  • extendDefaults: false replaces the default watch list with watchPaths alone. Turning it off asks: "default watch list dropped".
  • Removing an entry from watchPaths asks: "watchPaths loses N entries".
  • disableAllHooks: true in either settings file, removing a Guardian hook, changing its matcher or command, or lowering its timeout asks. The hook reads settings.json and settings.local.json together for these, as Claude Code merges them.

guardian list-watched prints the effective list: defaults on or off, custom watch paths, ignored paths. It ends with the line "Exemptions: only otlcGuardian.ignorePaths in .claude/settings.json. The hook asks before an agent adds one."

History of the otlc-guardian:doc marker

VersionBehavior
1.1.0Added as a "doc-exempt marker" for security spec files that discuss injection patterns. A write whose content carried otlc-guardian:doc skipped the hook's scan.
to 1.4.1Unchanged. Any payload could exempt itself by including the marker, and the hook's warning text told the model the marker existed. Logged as BUG-021.
first 1.5.0 buildThe marker in the content was ignored, but a marker already on disk was honored. Review finding 3 showed the two-step bypass: write a marker-only file, then the payload.
1.5.0 (HEAD)The hook does not read the marker at all, in the content or on disk. ignorePaths is the only exemption. BUG-021 is SMOKE-TESTING.

Three tests in tests/hook.test.js hold this in place: a marker inside the content is denied; the two-step bypass is denied (in bypass mode); and "a marker on disk exempts nothing, even when a person put it there". The audit never had code for this marker (see above). README.md's fork advice still tells forks to keep both marker names "intact", though otlc-guardian:doc no longer does anything.

Where no exemption is needed, or none exists

  • Existing quotes in a file. The hook judges a write by what it adds compared with the file on disk (scanChange()). Editing a spec that already quotes attack phrases, or Guardian's own section in a CLAUDE.md, is not blocked. Adding a new copy of a pattern is. SETUP.md "Hook exemptions" says most documentation needs no exemption for this reason.
  • The web content hook (web-content-guard.mjs) reads no settings and has no exemption; its header says its tool list is "intentionally NOT configurable via .claude/settings.json yet". It is advisory only and never blocks. SETUP.md "Customizing the watch list" says "Both hooks honor an otlcGuardian config block"; the code shows only the PreToolUse hook does.
  • The runtime guard (security/01-injection-guard.js, injection_guard.py) has no exemption parameter or marker.
Open on 2026-11-10

BUG-058 (IN-PROGRESS): hook ignorePaths is a substring match (fix staged in staging/, not yet live). BUG-038, where a comment naming the CSP header cleared WEB-002, is fixed in the audit (2026-11-10).

When to use one

Use an exemption only when the finding is wrong, and only in a way a reviewer can see. That is Step 3 of the OTLC-Guardian skill: "Never suppress a finding because the fix is inconvenient." For the audit that means an allowlist line with a real reason, per rule wherever the finding concerns one sink; it is preferred over the marker because it is one reviewable line in one file, takes precedence, and carries a written justification. Anyone with write access can add either, an agent included, because the hook does not watch security/.audit-allowlist or source files. The safeguards are the reason field, the exempt summary on every run, and CODEOWNERS review where it is set up. For the hook, the person approving the prompt decides.

Known-bug tests are not suppression. When a rule gets a case wrong, the case is logged in BUGS.md and kept as a knownBug() test in tests/audit.test.js, which fails the suite once the bug stops reproducing. The rule is never loosened to make the case pass.
