08

Inbound files

guardian inbound-check: how one file that arrived from outside is judged before anything uses it, what each of the eight checks does, the contract with DevNeural's mail daemon, and what the check does not see.

guardian inbound-check judges one file that arrived from outside and answers clean, hold or block. It exists for Lex's mailbox (BUG-086): Michael's rule of 2026-11-12 is that Guardian checks every file that arrives there, and DevNeural's daemon ingests nothing without a clean verdict. The code is security/inbound/, new in 1.5.0 and live (it is not part of staging/). It uses Node built-ins only.

The file is only read. Archives and documents are walked in memory, nothing is extracted to disk, nothing is opened by its own application, and no network is used. A check that cannot do its job never reads as clean.

How it is called

ItemValue
Commandnode bin/guardian.js inbound-check <file> [--meta <json-file>] [--json] (runInboundCheck() in bin/guardian.js)
--jsonstdout holds the verdict object on one line and nothing else. Without it a short report is printed: file, type, size, sha256, verdict, each reason, the state of each check, the entry count.
--metaA JSON file with what the mail said about the file. Known fields: source, from, to, subject, message_id, received_at, original_name, content_type. Only string values are kept; every one is untrusted text, judged and never run. source: "mail-body" marks a message body.
Exit code0 clean, 10 hold, 20 block, 2 usage or internal error (EXIT_CODES). The exit code repeats the verdict.
Exit 2No file argument, an unknown argument, a meta file that is not readable JSON or not a JSON object, a path that is not a file, a file that cannot be opened (locked, no permission, or refused by the machine's real-time protection), and any failure to load or run the check. ImportcheckInbound(filePath, meta, options) from security/inbound/index.js. For Guardian's tests only: options swaps the limits, the clock, the platform and the antivirus runner. The daemon calls the CLI as a child process.

The walk

The check numbers used in the code and the tests (check 1 type, 2 executables, 3 Office, 4 PDF, 5 archives, 6 encryption, 7 prompt injection, 8 antivirus) are the plan's numbering. CHECK_NAMES lists them in that order; PIPELINE runs them in the order of the figure.

For a message body (meta.source is mail-body) the archive and executable checks are reported skipped on the top-level file and do not count against clean: a body is not an archive and is never executed. A body whose bytes are not text or HTML holds as body-not-text, or blocks when the bytes are a program.

The verdict rule

Each check reports reasons with a severity: block, hold or info. The worst severity over all reasons is the verdict. An info reason explains and changes nothing.

What happened in a checkIts state in checksEffect
Ran, no block or hold reasonpassnone
A hold reason, or bytes that do not follow their format (FormatError, reason <check>-unreadable)holdhold
A block reasonblockblock
The check threw anything else (reason internal-error)errorhold
Did not apply (archive and executable on a mail body)skippednone
Should have run and did not (reason check-not-run)skippedhold
A limit was reached (LimitError)the state of the check that met itthe walk stops; hold, or block for a decompression bomb. Checks the stop kept from running are skipped with no second reason: the limit is the reason.

The same reason (same code, path and detail) is recorded once. A reason's detail is cut at 300 characters.

An inner path is the entry's name in its archive. Levels of nesting are joined with !/ (security/inbound/paths.js), so plc.zip!/main.L5K is main.L5K inside plc.zip inside the checked file. A / is a folder inside one archive. gzip is a transparent layer: the entries of a.tar.gz are the tar's entries, and a gzip of one file lists that file under its stored name.

Type: the bytes decide

detectType() reads magic numbers and structure; the name is never trusted. The name on disk, the name as sent (meta.original_name, when its extension differs) and the declared content type are compared with the result afterwards. EXPECTED lists what each extension's bytes may be; an extension it does not list is not judged. A file is text when it carries a Unicode byte order mark, or holds no NUL byte and almost no other control characters; UTF-8 is tried first and anything else is read as Windows-1252.

Executables, and the two meanings of .scr

A program blocks at the top level and inside any archive or document, by its bytes (PE, DOS, ELF, Mach-O, MSI, LNK, a Java class or archive, an Android or Windows app package, WebAssembly, compiled help, a #! script) or by its name (EXECUTABLE_EXTENSIONS: a .ps1 or .js is text and still runs on a double-click).

.scr is a Windows screensaver, which is a program, and also an AutoCAD script, which is plain text. The bytes decide (Lex, 2026-11-12). A .scr that is a program blocks like any other. One whose bytes are type text holds as autocad-script: Windows cannot run it, but AutoCAD runs its commands when someone loads it, so it is never clean. A .scr that is HTML, XML, an archive, unknown bytes or empty still blocks as executable-name.

Office and PDF: embedded files are judged as files

The Office check covers Office Open XML (the archive check has already read the parts), OpenDocument, legacy compound files (.doc, .xls, .ppt, OLE objects, MSI) and RTF. Every file embedded in a document (an Office embedding, an OLE package's payload, a compound file under any part name, a PDF's embedded files) goes back through the whole walk as a node of its own, so a program inside an OLE package blocks. Encrypted documents are recorded on the node and held by check 6.

The PDF reader finds every object by scanning for N G obj and does not trust the cross-reference table, so an object that an incremental update or a damaged table would hide is still read. An encrypted PDF holds: its strings and streams cannot be read, though its names still are.

Archives

zip (zip64 included), tar (ustar, pax, GNU long names) and gzip are read. The zip's central directory is the list judged, because it is the list an extractor uses. Every entry is read in memory and judged like a file of its own. A zip that is an Office or OpenDocument file is read here too, so the path, bomb and damage rules apply to its parts; the parts then go to the Office check and are not listed as entries.

Prompt injection: one rule list

Every text a file carries goes through scan() from security/01-injection-guard.js, the rule set the hooks use (chapter 03). There is no second pattern list. Text longer than the scanner's cap of one million characters is read in windows that overlap by 2,048 characters. Text is pulled from:

Two things are mapped in this check only, on the one rule list (Lex, 2026-11-12).

Weak rules. Three rules match ordinary engineering prose as often as an attack (WEAK_RULES). One of them as the only rule that hits in a text is the info reason prompt-injection-weak and does not hold. Hits are counted by rule id, per text: a second, different rule in the same text makes both hold, and every other rule holds alone. A rule is added to the set only with evidence from ordinary documents.

RuleWhy it is weak alone
GUARD-INJ-011"simulate a ..." is how engineers write about test runs (simulate a jam, simulate the load)
GUARD-INJ-015<user> and <system> are placeholders in manuals, command syntax and configuration notes
GUARD-INJ-028A file glob such as src/*.py followed later by */ reads as a comment holding a control word

Invisible characters. GUARD-INJ-UNICODE is mapped by character (classifyInvisible()). Characters used to smuggle text hold: Unicode tag characters, bidi overrides and isolates, the deprecated format characters U+206A to U+206F, a run of two or more variation selectors, and a run of zero-width characters that is eight or longer, or two or longer against a word. Typographic ones on their own are the info reason invisible-characters: soft hyphens, narrow spaces, a lone zero-width joiner or non-joiner, direction marks, a byte order mark. Mail padding and emoji use them.

The antivirus check

The file as it sits on disk is scanned once, after the walk, by whichever antivirus engine protects the machine. Guardian changes no antivirus setting, adds no exclusion, fetches nothing and removes nothing. There is no EICAR self-test. The engine is named in antivirus_engine and in each reason.

EngineUsed whenHowReading the answer
1. Windows DefenderThe WinDefend service is running (sc.exe query, read by the state number, which does not change with the display language)MpCmdRun.exe -Scan -ScanType 3 -File <path> -DisableRemediation. Defender unpacks archives itself and gets the file only.Exit 0 is clean. Exit 2 with no failure reported is a threat. Exit 2 with "Failed with hr" holds, as does any other exit code. It is gated on its exit code only; Security Center is not asked (Lex's ruling).
2. The registered AMSI providerDefender's service is not running. The script decides nothing: it prints one line of JSON, and antivirus.js reads the numbers.AMSI_RESULT_DETECTED (32768 or more) blocks. Clean is 0 or 1 only. Why the AMSI engine is a script file

The child is started as powershell.exe -NoProfile -NonInteractive -NoLogo -ExecutionPolicy Bypass -File amsi.ps1, hidden. It is never started with -EncodedCommand or with -Command and generated code: a command line with encoded script text in it is what an antivirus's behaviour shield flags, and the first build's -EncodedCommand child was flagged by one on 2026-11-12. A plain script file is something an antivirus can read. The command line is the same for every file and holds no script text.

Why the file's path and name travel in environment variables

The file's path and name reach the child in GUARDIAN_AMSI_FILE and GUARDIAN_AMSI_NAME, never as arguments. A name is untrusted, and PowerShell would bind a name that starts with a dash as a parameter of the script. The chunk size and overlap travel the same way (GUARDIAN_AMSI_CHUNK, 16 MiB; GUARDIAN_AMSI_OVERLAP, 64 KiB). A file larger than one buffer goes through in chunks, each starting with the last 64 KiB of the one before, so nothing is cut in two unseen.

Security Center state and antivirus-disabled

A provider whose product is switched off answers "clean" to everything. So for the AMSI engine the product behind the provider must be listed as enabled by Windows Security Center (root/SecurityCenter2, AntiVirusProduct, productState bit 0x1000). A provider DLL is matched to its product by a shared vendor folder (drive, Program Files, vendor), and Defender's MpOav.dll by the windowsdefender: product path. When the product is off, or Security Center lists no product for the provider, the check holds as antivirus-disabled and the file is not scanned. When Security Center cannot be read, it holds as antivirus-error.

Archive entries go to AMSI one by one

AMSI sees only the bytes it is handed and does not unpack an archive. So every file.inner entry goes to the child and is scanned as a buffer of its own, under its inner path, in the same AMSI session. A detection in an entry blocks with that entry's path; a failed scan of an entry holds with it. The child must report as many entries as were sent, or the check holds.

Limits of this design
  • The entries are kept in memory from the walk until the antivirus check: the buffers the walk already read, at most the 1 GB uncompressed limit in all. They are sent to the child as one buffer on standard input (encodeEntries(): for each entry the length of its path, the path in UTF-8, the length of its data, the data), so the peak is about twice the uncompressed size while that buffer is built. With Defender they are kept and not sent.
  • Only file.inner entries are handed over. Parts inside a document (the members of a .docx, a file embedded in a PDF) are not sent one by one; the engine sees them only as part of the file on disk.
  • The antivirus runner's signature is (path, timeoutMs, name, entries) => { engine, status, detail, findings? }, with status one of clean, threat, unavailable, disabled, error. Tests pass their own runner in options.antivirus.
  • Whether the engine consults its vendor's cloud is that engine's own setting, outside Guardian.

The daemon starts the CLI with a minimal environment, so programs are found from %ProgramFiles% and %SystemRoot% when set and from C:\Program Files and C:\Windows otherwise, and the AMSI child is given a temp folder to compile its interop type in.

Why the check is named antivirus

The plan called check 8 defender. A machine protected by a third-party antivirus has Defender's service stopped, and every file would have held there. The check was renamed antivirus and given the AMSI engine at the same contract_version. antivirus_engine reads "Windows Defender (MpCmdRun)" or "AMSI provider" followed by the provider's DLL and the product's name.

CAD files

The CAD files a customer sends (STL, STEP, IGES, DWG, DXF) come out clean when they are what they claim (Lex's ruling). STEP, IGES and STL have no magic number worth the name, so security/inbound/readers/cad.js knows each by its structure.

FormatKnown byRead for text
STEP (step)Starts with ISO-10303-21;, has a HEADER; and an ENDSEC;, ends with END-ISO-10303-21;Whole file
IGES (iges)Every line is 80 columns; column 73 runs through the sections S, G, D, P, T in that order; columns 74 to 80 are a sequence number; one T line ends the fileWhole file
ASCII STL (stl-ascii)Starts with solid, continues with facet normal or endsolid, and its last line starts with endsolidWhole file
Binary STL (stl-binary)An 80-byte header, a triangle count, and exactly that many 50-byte triangles of twelve finite floatsThe header

A .stl, .step or .igs that is plain text and not built as the format says is judged as the text it is: clean, with a type-mismatch info, and read whole. A binary .stl whose size does not match its triangle count, or that holds a number that is not finite, is unknown and holds as unreadable-type.

What the check does not see

Known limits
  • Formats recognised and not read inside. DWG, binary DXF, audio and video files, and images other than PNG and JPEG are known by their bytes and are clean when the name agrees. Their content is not read for text. The antivirus still scans them.
  • Pixels. No image is decoded and nothing is read by OCR. Text drawn into a picture, a scanned PDF page included, is not seen.
  • PDF text with no Unicode map. Text in a composite font with no ToUnicode map is glyph numbers. It is counted and reported as pdf-text-unmapped (info), never guessed.
  • A reworded instruction. Detection is pattern-based, as in the runtime guard: an instruction that matches no rule passes. A weak rule alone does not hold.
  • Archive formats with no reader (7z, rar and the rest) hold; they are never opened.
  • Off Windows every file holds, because the antivirus check cannot run.
  • What the file does when opened. Nothing is run. A document with no macro, script, link or embedded object that still exploits its reader is caught only if the antivirus knows it.

Known bugs

State on 2026-11-12

BUG-086 (SMOKE-TESTING): the check is built and its suite passes. It stays in smoke test until DevNeural's daemon has run it on real mail.

Who depends on it

  • DevNeural's mailbox ingest. The mail daemon runs the CLI as a child process on every body, attachment and archive entry before Lex reads anything (DevNeural docs/spec/LEX-MAILBOX.md, sections 5 and 6). It reads the exit code and the verdict object, requires file.sha256 to equal the hash it recorded, and unpacks an archive only against file.inner. Anything that is not a clean verdict at a contract major it knows is a hold. Chapter 07 has the row.
  • The contract. contract_version is an integer major. A change that keeps every field and meaning stays at 1; new reason codes and a new ruleset_version need no daemon change. A change to a field's meaning, an exit code or the verdict rule is a new major, shipped behind a flag until the daemon accepts it. DevNeural's Lex is told of every change to the check's output in the same piece of work.
  • The scanner. The injection check imports scan and INJECTION_PATTERNS from security/01-injection-guard.js. A pattern change there changes verdicts here and gives a new ruleset_version.
  • Installed projects. guardian init and guardian update copy security/ whole, so security/inbound/ reaches every project that installs Guardian. The CLI loads the check from Guardian's own folder, not from the project's copy.
